rust/v0.0.3Packed step scratch, and batched steps on num_gpus cards

The second prototype of the redesign in docs/rust-redesign.html ("Rust rebuild: steps, the memory budget and rustflow"), built against the design as it stood on 2026-11-24. It covers items 1 and 2 of that document's order of work and nothing more:

  1. The core, device-free. The MainBus's flow layer, the declared view, the budget with its counters, flag, table and final node, the heap slab, and what is new since v0.0.2: step scratch declared per step and packed by the DAG's transitive closure, the lower bound in the budget table, a lease that borrows for the length of run, one layout function per step, the NaN fill, and caps clamped to what the machine has.
  2. Batched steps on num_gpus cards. No library stream: a stream per GPU step per card, one lock and one fixed 128 MiB BLAS workspace per card. eri builds B in batches of shell pairs and keeps it on the host heap; jk builds J and K of the SAD density over batches of aux functions, each card contracting its share, reduced onto gpu0.

The SCF and the rest of the DF-RHF chain (item 3) are not here. Throwaway: a crate and a workspace of its own, in no gate, never to be merged into rust/.

This box has one CUDA card. Everything is written for num_gpus cards, and the multi-card path is run with two logical cards aliased onto device 0 ([resources] devices = [0, 0]), each with its own lock, workspace, streams and scratch slabs. That exercises the lock order, the per-card rows and the reduction. It is not a multi-GPU run: real multi-card was not run, and no number here says anything about scaling.

The old path is add_packed_b under the planner and the arena, with every pair kept; it runs the same kernels, the same Cholesky and the same fb_recipes_sys::trsm, so this row holds the batching and the layout, not the kernels. The replay's B, J and K differ from the run before it by nothing the bars see.

Beside those, on the same runs:

  • An over-cap plan is refused with the whole table. Water needs 129.72 MiB of device memory (128 MiB of it the handle workspace); with device_cap_mib = 129 the final node refuses it and prints every step's row, the packed scratch, the lower bound and the workspace.
  • A cap the card cannot meet is clamped, not an abort. device_cap_mib = 1000000 runs; the table prints cap as written 976.56 GiB beside cap used 8.82 GiB, the card's free memory at setup.
  • A limit too small for one batch is refused naming the step, its limit and its least bytes: step 'eri': its limit of 10.24 KiB holds no batch: the narrowest, of width 36, takes 529.50 KiB of device scratch per card, and the same for jk (width 1, 16.81 KiB).

One-off times, debug build at opt-level = 1, a card that also drives a display. They say what a batch costs here and are not a benchmark. Benzene's eri takes 52 ms in 6 batches and 347 ms in 206: about 1.5 ms a batch, the price of one blocking sync and one launch set per batch. On two logical cards the same 206 batches take 191 ms. Both cards are device 0, so that is two streams overlapping each other's waits on one card, not two cards.

Run it

git submodule update --init --recursive
(cd rust && cmake --preset cuda && cmake --build --preset cuda -j12)   # the libraries the crates link
cd experimental/rust/v0.0.3
cargo test                                                       # 17 device-free tests, 2 doctests
cargo test --test gpu -- --include-ignored --nocapture --test-threads=1   # the 4 GPU cases
cargo run --release --example run -- examples/h2o.toml                # setup, budget mode, execute mode
cargo run --release --example run -- examples/benzene_two_cards.toml  # two logical cards on device 0
cargo run --release --example run -- --budget-only examples/h2o.toml  # the edges and the table, no device

The GPU cases use device 0. On this box hold both of the card's locks around them (flock ~/.sccache/gpu-locks/cuda.0.lock flock …/cuda.1.lock cargo test …).

The packed scratch of that run, card 0. records, eri and jk lie on one path, so all three start at offset 0. guess is ordered against jk alone, so in the pinned slab it sits above eri and under jk's region. Each slab is at its lower bound, which here is its largest single declaration, jk's.

Each device cap is half of the card's free memory less half its margin: two logical cards on one device share its reading. B is the heap column: 28.39 MiB on the host, on no card.

The locks of that run. eri and jk each declared the library on both cards, so the wrapper took card 0's lock and then card 1's, bound each card's handle, ran, synchronized both streams and only then released.

What the prototype says to change

Ordered by how much each bears on the design document.

  1. One handle set per card cannot be built on fb-core-wwr as merged, and the prototype did not build it. BlasHandle keeps the Arc<Stream> it was made on and has no rebind. fb_recipes_sys::trsm takes its kernel stream from that owner (blas.owner()) and its gemms from the handle, so a handle rebound through the raw SetStream would run one solve on two streams with nothing ordering them. BlasHandle::bind_workspace also takes ownership of the workspace and synchronizes the owner's stream, where the design's workspace is the card's and outlives every binding. So the prototype holds one BLAS handle per library-using step per card, made in budget mode on that step's own stream: two per card here. What is per card, as designed, is the lock and the one 128 MiB workspace, which every handle on the card is pointed at when its step takes the lock (raw SetStream to its own stream, then raw SetWorkspace, every time). That is the "handle set per step" the design rejected for its cost on HIP. Three ways out, for the document to choose between: (a) BlasHandle::rebind(&mut self, Arc<Stream>, workspace), one function, with the recipes reading the stream from the current binding; (b) every recipe takes its stream explicitly, as cholesky_diagonal and symmetrize already do; (c) no rebind at all: the card's handle keeps its creation stream, and a library-using step runs on that stream while it holds the lock. Under (c) the safety argument is unchanged (everything the holder enqueues is on one stream, synchronized before the lock is released), SetStream is never called, and the cuBLAS ordering hazard goes away. It gives up a step's own stream object for library users, which already never overlap on a card.
  2. "The default cap is read after the handles exist" depends on item 1. Here the handles are made in budget mode, after the reading, so their memory (8 MiB each on cuBLAS by the design's handle measurements; not measured here) comes out of the margin, and it grows with the number of library-using steps. With one handle set per card made in setup, the sentence holds as written.
  3. A step's limit has to say what it covers. eri's scratch is a batch plus O(N²) residents that no width removes: the Cartesian metric, its half transform, U_aux, the records. On water the narrowest batch needs 529.50 KiB, of which the batch itself (its two tensors and its cells, by the layout's arithmetic) is about 93 KiB. "The widest whose bytes fit the step's own limit" was implemented over the whole region, so a limit below the residents is a refusal however narrow the batch. The document should say whether the limit bounds the batch or the step's scratch, and the refusal's "least bytes" should name the two parts.
  4. mem_budget is not a function of the dimensions and the options alone: the cap enters. The default limit is a fraction of the card's cap, so the width, and with it every scratch row, depends on the reading. A dry budget has no card to read, so its defaulted cap is none and its table shows one batch per class, not what the run will use. Either the device-free budget takes a cap, or the document says the table is exact only under an explicit cap or limit.
  5. Pinned scratch forces a sync per batch, or a ring. A batch's cells are written into pinned scratch and its result is downloaded into pinned scratch; the next batch may not touch either until the card has finished with them. With one tenant of each, that is a blocking sync per batch: about 1.5 ms a batch on benzene, 6.7 times the 6-batch build at 206 batches. Overlapping batches needs a ring of pinned tenants and device events inside the step, and the ring's depth is then part of the step's layout and of what its limit holds. The design covers this in one clause ("a streamed pass still needs device events"); it deserves a paragraph in "Sizes: batched only", since every batched step meets it.
  6. Setup builds a pair-scaling array to count from. The lengths eri and records need come from fb_integrals_mmd::record_tables, which builds the bra, ket and record-prefix arrays of every shell pair on the plain heap. That is what "setup counts every length that scales; it builds none of those arrays" rules out. It is small (three integers a pair), but the rule as written needs either a counting walk in fb-integrals-mmd or the tables as a step's HeapSlab.
  7. The layout function should be called by the wrapper, once. A Span is consumed when it is carved, so the tenants of one layout cannot be handed out twice; two calls of the layout function can. Nothing in the types stops a run from calling it twice and holding two slices of the same pinned bytes. Making the layout an associated type of Step, built once by the wrapper and handed to both mem_budget and run, closes that and removes the one place the two could disagree. What catches a disagreement today is a panic when run carves past the declaration.
  8. An all-GPU step's layout is per card, and gpu0's differs. jk needs D and fragments of J and K in scratch on every card but gpu0, which reads and writes Outputs. The width is then held to the largest card's layout (169 aux on two cards, 170 on one, at the same limit). "A row per card" is right; the size function takes the card.
  9. Largest-first is at the bound less often than the model says, on other sizes. On this prototype's random DAGs (2 to 16 steps, an edge with probability 0.25, sizes uniform over 1 to 40 units where the model's are log-uniform over 1 to 2048) first fit largest-first is at the lower bound on 2467 of 2973 (83.0%), 1.453 times the bound at worst, against the model's 98.1% and 1.281. Safe on every one. The lower-bound row is what shows it, and it argues for keeping the door open to the best of four orders. On the real graphs here it says nothing: they are near-chains, and each slab is at its bound, the largest single declaration.
  10. run needs its lane mutably, and its inner tasks need a way to split it. BlasHandle is Send and not Sync, so a step that fans out over cards hands each inner task one card's lane by &mut. The view therefore no longer carries the lane; run takes (out, view, lane, scratch). The fan-out here is scoped threads, one per card, and not a rustflow subflow.
  11. B written by several cards needs an unsafe, or a staging pass. B is pair-fastest, so two cards' batches interleave in memory and no slice cut parts them. The prototype scatters each batch through a raw pointer, with "a batch owns its columns" written beside it. This is a second unsafe of the memory model that the design's enforcement table does not list.
  12. The reduction and the broadcast went through the host. D reaches the other cards, and their fragments reach gpu0, by a download, a host sum and an upload, with no collectives. With one card nothing is copied. The document says where the result lands, not how it gets there.
  13. Dims carries per-class counts. A batch never spans two classes, so the batch list, and eri's cells bound, need each class's pair and record counts. Dims is a small vector longer and no longer Copy.
  14. Logical cards are worth keeping as a test facility. devices = [0, 0] ran the lock order, the per-card slabs and the reduction on a one-card box for the cost of a list in the config. It cannot show contention between real cards, a wrong current device (both are device 0), or any scaling.

Not run

  • Real multi-card. One physical card. Two logical cards share its context, so a launch on the wrong card's context cannot fail here, and the per-inner-task device selection is exercised only as code that runs.
  • HIP. CUDA only. The SetStream then SetWorkspace order, rocBLAS's hard need for the workspace and the hipBLAS pool are untested here.
  • One handle set per card, as item 1 says, and any solver handle: no step here calls syevd, so a solver work buffer in step scratch and the binding's size check are not exercised.
  • The SCF and the DF-RHF chain (item 3 of the order of work): jk runs once, over the SAD density. No condition loop, no energy, no comparison with PySCF beyond what the old path's B carries.
  • Contention on a card's lock. eri and jk are ordered, so neither ever waited for the other. No two unordered library users exist in this DAG.
  • The NaN fill's power on the device. The device regions are filled with 0xFF before run and the results hold, which says no step here reads stale device scratch. No step was written to fail under it on a card; the failing case is core's, on the heap.
  • The enforcement checks: the clippy bans, the allocator record, the unbudgeted-heap row of the table.
  • The default limit fraction. DEFAULT_LIMIT_FRACTION is 1/8 of the card's cap, a placeholder: the design leaves the value open, and nothing here measures it. At these sizes it never binds.
  • Screening. Every shell pair is kept. B is budgeted at the unscreened bound, which is then also what is used.
  • A size where B does not fit a card. Benzene's B is 28 MiB. The path is the one a larger molecule would take, and it was not timed at one.
  • Batches kept on the cards between passes, the sentinel tests, packing Outputs, several nodes: proposed or set aside in the design, not built.

Crudest form, spelled out

  • eri: one batch in flight per card; the transpose into B's rows is the host's scatter; every card computes its own metric and factor; no screen.
  • jk: K from D with no occupied factor; every pass uploads all of B; a host copy of J and K is kept in the Output for the tests.
  • records: no screening bounds; built on every card, one card after another.
  • Setup: a neutral closed-shell molecule, built-in bases.
  • Budget has no pinned Output kind: every pinned byte here is scratch.
