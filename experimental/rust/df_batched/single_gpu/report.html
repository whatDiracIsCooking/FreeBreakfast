Batched DF factor B on one GPU

rust/'s add_packed_b already runs the fused loop: (P|mn) for every P over a batch of shell pairs, fitted against a resident L, downloaded as B. It never puts a whole (mn|P) or B on the card. The build is compute-bound on one stream, and two thirds of its time is the spherical transform.

67%of gly20's device time is the spherical transform; the trsm is 27%, the integrals 4%
60%of gly10's device time is one dense GEMM against the block-diagonal U_aux (nsys)
1.0%of gly20's device time is the D2H download of B

The loop

Everything O(N²) stays on the card: the records, the aux tables, U for both bases, the metric and its Cholesky factor L. The loop runs over batches of shell pairs, one counted loop per class (la, lb), with ring depth 2. A batch never spans two classes. Each trip does five things:

  1. packed three-center: (P|mn) for every aux function and the batch's pairs, FelizJueves' packed peri3 kernels, Cartesian P.
  2. spherical transform: a dense GEMM W = U_auxᵀ X on the aux index, then strided-batched GEMMs for the ket and bra.
  3. density fit: the trsm L B = (P|mn) in place.
  4. B (la, lb) batch transpose: one geam from aux-fastest to pair-fastest.
  5. download and unstage: a pitched copy into B's heap row on the host.

Batching over aux functions instead would not work. Every column B·,mn depends on every P, so a P batch cannot be fitted on its own. The batch width is the planner's adaptive part, the widest that fits the device room. Driver: experimental/rust/df_batched/single_gpu, which calls the unchanged rust/ crates.

One trip, on the device

Everything runs on one stream. The ring of depth 2 overlaps the host's table building and unstaging with the device. On the device, the download queues behind the trip's compute rather than under the next trip's. So does each trip's upload of its packed three-center cell tables, which is about as large as the B batch it downloads. Both copies together are 2.2% of device time, so a copy lane would win back at most that much.

The dense aux GEMM is the lever. U_aux is block-diagonal by shell, so almost all of that GEMM multiplies zeros. FelizJueves #743 (upstream 6e1c341, newer than the pinned submodule) emits speri3, which writes Q already spherical by Hobson's theorem. FreeBreakfast #1736 takes it into rust/. That removes this GEMM outright, and the bra/ket GEMMs and the kernel's output shrink by the Cartesian-to-spherical ratio of the aux set. It is left to its own PR. This page measures the current path as the baseline.

A room smaller than the prefix's own rows (the metric and L, 2 × naux² doubles) leaves no room for the loop. The planner then sets the width to 1, one shell pair per trip, and the pipeline's admission step would refuse that plan. The driver skips admission, so those rows ran anyway. They give the loop's fixed cost per trip at the extreme.

"B vs first" is the largest |ΔB| against the first room's B, all held in one process. The GEMM and trsm shapes change with the width, so B agrees to rounding (worst 9.8e-13), not bitwise.

Two passes against the fused loop

The two-pass scheme builds all of (mn|P) and moves it to the host, then uploads it again to fit. Its (mn|P) is the same shape as B. It moves 3·|B| over PCIe against the fused loop's |B|, and holds 2·|B| on the host until the first buffer is freed.

The fused loop's real advantage is host memory. The build is compute-bound, so the extra PCIe traffic would add only a few percent. The second |B| on the host is what limits molecule size: gly20 needs 23.11 GB in two passes against 11.56 GB fused.

How it was run

  • Driver df-batched (this crate), release build, against rust/build-cuda. Commit cb30cc80, FelizJueves 826b69e.
  • Each run: one warm-up, then 3 timed runs, median. Both CUDA locks held, the card otherwise idle.
  • Timeline: nsys profile -t cuda, exported to SQLite, then report/timeline.py.
  • Page: report/make_report.py over the JSON files. No number here is typed by hand.
