Experiment · 2026-11-24 · RTX A6000, one card · correctness only, no timing yet

B with no spherical transform

../single_gpu builds the density-fitting factor B with rust/'s add_packed_b. There, each batch's integrals come out with a Cartesian bra, and a GEMM transform makes them spherical. FelizJueves's ssperi3 kernels (#745) write all three indices spherical already, so the transform step is gone from the loop. The resulting B matches rust/'s to 1.3e-13 relative on gly10, and to 2e-14 on water through f.

What changes

B[Q][μν] = Σ_P L⁻¹[Q][P] (P|μν),   M = (P|Q) = L Lᵀ

Both builds loop over batches of shell pairs, never over aux functions, one counted loop per class (la, lb), ring depth 2. Everything O(N²) stays on the card (records, metric, L); the O(N³) tensors never do. Only the contents of a trip differ:

rust/'s add_packed_b (--baseline)

  1. speri3<la, lb, lP>: (ab|Q), a b Cartesian, Q spherical
  2. spherical transform: two strided-batched GEMMs per class against U
  3. density fit: trsm against L
  4. transpose (geam), pitched download into B

Device rows per trip: the tables, the Cartesian batch, the transform's ket scratch, then three rows of naux × spherical columns. Plus U for the orbital basis, uploaded once.

this experiment (default)

  1. ssperi3<la, lb, lP>: (μν|Q), all three spherical, each pair at its spherical column
  2. spherical transform
  3. density fit: trsm against L, add_batch_fit unchanged
  4. transpose (geam), pitched download into B, unchanged

Device rows per trip: the tables and three rows of naux × spherical columns. No U, no Cartesian batch, no scratch, so the same room plans a wider batch. The width counts spherical columns.

Each ssperi3 cell writes element (μ, ν, q) at dst + n_aux (μ (2lb+1) + ν) + q. A diagonal pair writes its full square spherical block. This is the pair map's spherical layout (PairMap::sphe), which the trsm already reads. A cell's destination is therefore its pair's spherical column in the trip × naux + the aux shell's first function. Each cell zeroes its own elements first, so nothing is zeroed beforehand. For s and p bras the kernel body is speri3's.

Why these numbers pass

  • The size is roundoff. Both paths contract the same integrals by the same harmonics, in a different order: in-kernel, per primitive triple, against a GEMM over the finished Cartesian block. Both then go through a trsm against L, which amplifies any input difference by L's conditioning. A wrong index, layout or harmonic would show up at the size of |B| itself (~0.2–1.3 here), about 10¹² times larger than anything seen.
  • Water's s and p classes are bitwise; gly10's are not. For s and p the kernel is speri3 and the transform is exact, so the integrals agree bitwise on both paths. The likely cause of the gly10 difference is the trsm: the two paths plan different widths in the same room (no Cartesian scratch), so cuBLAS solves different column partitions. Water fits each class in one batch on both paths. Bitwise equality is not a goal here.
  • The f classes are covered. FelizJueves tested ssperi3 on a card only at (aa|p), and no la ≠ lb class there. Water in cc-pVTZ runs every orbital class through (ff), against aux through g, at ≤ 6.5e-14.

What is here

file
kernels/emit.pyEmits the 70 ssperi3_{la}{lb}{lP}.cu units (la ≤ lb ≤ f, lP ≤ i) and ssperi3.h from deps/FelizJueves. It works like tools/emit/packed_three_center_kernels.py does for speri3, with spherical_bra=True added.
kernels/ssperi3_launch.cufbx_ssperi3_packed_class: rust/'s fb_three_center_packed_class over the ssperi3 table, with the same arguments and refusals. CUDA only; returns cudaGetLastError().
kernels/CMakeLists.txtA CMake project of its own, which runs emit.py at build time (nothing generated is committed) and builds libfbx_ssperi3_kernels.so with relocatable device code, as rust/'s kernel libraries do.
src/ssperi3.rsadd_packed_b_spherical: a fork of rust/'s add_packed_b and add_packed_three_center_tasks. Each cell's destination is a spherical column, the transform and U are removed, and the batch's adaptive width counts spherical columns.
src/main.rsdf-batched-spherical: ../single_gpu's driver with --baseline and --check added.

It is a fork, not a reuse, for two reasons. The cells, the aux records and the class view are pub(crate) in fb_integrals_sys, so they are formed here the same way. And the kernel library is not rust/'s. Both sides link rust/'s crates by path, so --baseline runs rust/'s add_packed_b exactly.

FelizJueves must be at or past 6c9b85e (#745); this branch moves the submodule to 57ccc18 (#754). Re-emitting rust/'s speri3 units at that commit reproduces the committed ones byte for byte. The src/ emitters have not been re-run there.

Build and run

cd rust && cmake --preset cuda && cmake --build --preset cuda && cd -
cd experimental/rust/df_batched/single_gpu_spherical
cmake -S kernels -B kernels/build -G Ninja -DCMAKE_BUILD_TYPE=Release
cmake --build kernels/build          # emits and compiles the 70 units
cargo build --release

FB_RUST_BUILD_DIR and FBX_SSPERI3_BUILD_DIR point at other build directories.

df-batched-spherical --xyz gly10.xyz --check --reps 1            # B against rust/'s, then one timed run
df-batched-spherical --xyz gly10.xyz --room-mib 2400             # ssperi3, no transform
