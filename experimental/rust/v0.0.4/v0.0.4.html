rust/v0.0.4The design, and the prototype built from scratch

The design of the Rust rebuild as it stands at v0.0.4, and what v0.0.4 will build. A calculation is a DAG of steps on rustflow. Each step has one function that counts and allocates its memory up front, and one that runs. There is no planner. Nothing here is built yet: the code is the earlier prototypes ../v0.0.2 and ../v0.0.3, and nothing under rust/. rust/docs/ describes the tree as it is, and changes with the implementation.

This page is self-contained. It says what the design is now, not how it got here. Each prototype's page carries the whole design forward as it stands at that prototype; the earlier pages (../v0.0.2, ../v0.0.3) and git history hold the path. Measured claims name the experiment that measured them, under experimental/rust/ unless a path says otherwise. Open marks what is not settled; everything else is the design.

What v0.0.4 builds is the DF-RHF chain as steps, on num_gpus GPUs, batched. Like its predecessors it is throwaway: a crate and a Cargo workspace of its own, in no gate, never merged into rust/.

The shape

A calculation is a DAG of steps, as in the C++ src/pipeline. Every step implements MemBudget: mem_budget charges the counters for what the step will allocate, then allocates it. The same DAG runs in two modes over one rustflow Executor.

  1. Setup. Parse the config, the geometry and the bases on the host; fill Dims with every length a step's arrays need (counted, not built); make each GPU's stream and handles. Not budgeted.
  2. Budget mode. Each node calls its step's mem_budget: count, check, allocate into the MainBus. The final node packs step scratch and accepts or refuses the whole plan.
  3. Execute mode. Each node calls its step's run. Allocates nothing. Replays write into the same buffers.

There is no planner and no byte reuse between the Outputs steps pass on. A kind's peak is the sum of the steps' Outputs, plus packed step scratch, plus the fixed handle workspace. Step scratch is packed into one slab per GPU and kind, and two steps share bytes only where the DAG already orders them. No edge is added for memory, so work stealing cannot interact with memory.

Steps and the MainBus

The MainBus is a deliberate god object: one place that holds every step's Output. A step declares the Outputs it reads; the builder makes the DAG's edges from that declaration, and run receives a View of exactly those and not the bus. The steps and the MainBus live in one crate, so the bus can name every Output type with no dependency cycle.

  • An Output holds what outlives its step's run; scratch holds the rest. The DIIS ring, a Davidson subspace, the records and work lists, build intermediates: all step scratch.
  • The lock is used plainly. The owning step takes write(), a reader's View takes read(). On a chain it is never contended. A thin wrapper hides the standard lock's poisoning unwrap().
  • A step reads only what it declared. The declaration is the edge, so a missing edge is a missing declaration, and that does not compile: the View has no such field.
  • Only the owning step writes, by the visibility of an Output's mutating methods within the steps' crate. The one exception is a manager's mutable state, which its readers reach through the manager's lock (EriManager).
  • A step is one config table and one slot. [gradient] is one step; what it computes depends on the energy method the config names. No step type has two instances.
  • A step the config does not ask for is not in the DAG. A step that declares it reads one is refused when the DAG is built, naming both. So no declared read finds an empty slot; that the slot is filled is a runtime assert.
  • Shared code with per-user state is a type, not a step. DIIS: each user builds its own Diis in run over a slice of its own scratch, sized in its own mem_budget. The history lives exactly as long as the run.
  • An Output can be loaded from a file, in part or whole, as in src/pipeline. That is how a step is tested alone. Budget mode still allocates; the load fills.
  • A replay allocates nothing. What lives in scratch never carries over. What carries over in an Output (the last geometry's orbitals as the next guess) and what must be cleared (a converged flag) is each step's own business: a reset mode in the step, as v0.0.2 built it. Open: whether to make it explicit, as an on_replay the wrapper calls.
  • mem_budget is an associated function of Dims and the step's options (nroots, a subspace size), both read from the MainBus.

The EriManager

The density-fitted ERI is a shared product with state of its own: streams, a ring of buffers on every GPU, a cache. That state lives in one object, eri's Output, and its users call its methods.

pub struct EriManager {
    l: PerGpu<DeviceBuf<f64>>,   // the metric's Cholesky factor, every GPU
    b: HeapSlab<f64>,            // B, n_pair (unscreened bound) × n_aux
    state: Mutex<EriState>,      // per GPU: the ERI buffer, its streams,
                                 // events and the cache's contents
}

impl EriManager {
    /// J and K for each density, on gpu0. Every GPU contracts its own aux
    /// batches; the fragments are reduced onto gpu0.
    pub fn build_jk(&self, held: &mut Held<'_>, d: &[DeviceSlice<'_, f64>],
                    j: &mut [DeviceSliceMut<'_, f64>],
                    k: &mut [DeviceSliceMut<'_, f64>]);
}

A sketch, not a signature to hold anyone to. What is fixed:

  • It is eri's Output. eri's mem_budget allocates all of it: L on every GPU, B's slab on the host heap, and on every GPU the ERI buffer and its pinned staging. These are summed with every other Output, for the whole calculation. eri's run factors the metric, builds B and fills the manager; as the owner it reaches the state through &mut, with no lock.
  • Its readers declare it, like any Output. The edge comes from the declaration. A reader that calls its methods also declares its lock, and the wrapper takes it (lock order). B and L are immutable after eri; only the state behind the Mutex changes, and only under its lock.
  • The caller owns its results. build_jk writes the J and K it is passed, reads the densities it is passed, and keeps nothing of the caller's. A caller's own state (its DIIS, its Fock matrix) stays in the caller's scratch.
  • It takes a slice of densities. DF-RHF passes one. UHF passes two, and a response solve, a Davidson or a state average pass many: a J/K pass is bound by streaming B, so n densities cost about one pass. v0.0.4 sizes for one.
  • It never takes a lock. The GPU guards it uses are passed in, held by the wrapper; it has no path to a Mutex.

The ERI buffer. One device buffer per GPU of [eri] mem_per_gpu bytes, eri's step limit. eri's build and every later J/K pass run in it, one after the other, since the DAG orders eri before every reader:

  1. During eri's run it holds the build's ring: two pair batches in flight per GPU, each with its records and work lists.
  2. Afterwards it holds, per GPU, the J and K fragments, one aux batch's buffer for the J/K pass, and the cache: as many of that GPU's aux batches as the rest of the buffer holds. A pass uploads each uncached batch into the one buffer and syncs before the next; a ring of two there is Open until the per-batch sync is measured.

(μν|P) is spherical from the kernel. FelizJueves's ssperi3<la, lb, lP> (#745) writes all three indices as real solid harmonics, each pair's block at its spherical pair column, the layout the fit reads. No bra transform runs, and the ring holds no Cartesian batch, no transform scratch and no orbital U. It is plain FP64: the mixed-precision and screened forms of the same kernels are not used. No array in the DF-RHF chain has a Cartesian index.

B is built over pairs and contracted over aux functions. A pair column of B depends on every P, so a batch of P cannot be fitted alone; a batch of pairs can. Each GPU takes its own pair batches, forms (μν|P) in its ring, fits it against its own L, and downloads it into B's slab. No GPU needs anything from another. B is pair-fastest, so one pair batch's columns are a strided run in every row of P, and two GPUs' batches interleave in memory: no slice cut parts them. Each batch is scattered through a raw pointer, the second unsafe of the memory model, with its invariant beside it: the pair batches partition the pair columns, so a batch owns its columns and no two write one. A J/K pass then runs over aux batches: each GPU contracts its own, and the fragments are summed onto gpu0 through the host.

The cache. A GPU's aux range is fixed: the aux functions are split across the GPUs once, in budget mode, so GPU g always contracts the same batches. The cache fills on the first J/K pass, from the host copy (the build's pair batches are the wrong index order to fill it). Every later pass uploads only what is not cached. When a GPU's whole share fits, it uploads nothing after the first pass, and its aux batch is its whole share. A second copy of B is ruled out by size; the cache is a part of the one host copy, held on the GPUs.

What mem_per_gpu does, from config alone:

Set to Gives
Below the ring at a width of one A refusal naming [eri], its limit and the least it needs
About the ring Batched build and passes, no cache: the tests' many-batch case on water
Enough for the GPU's share of B One aux batch per GPU, nothing uploaded after the first pass
Default 2 GiB: a fixed constant, not a fraction of the cap, so --budget-only is exact. A placeholder; Open: the measured value

The buffer is held for the whole calculation, so what it takes is not available to later steps. The budget table shows it as its own row.

Derivatives of B are scratch. Gradients and Hessians build the derivative of B a batch at a time and contract it at once, inside the step that needs it. They read the metric and L, which is why the metric is a real Output and L is the manager's.

The memory budget

MemBudget the trait, mem_budget its function, budget mode the DAG run that runs it, Budget the handle it allocates through.

pub trait MemBudget {
    /// Charge what this step allocates, allocate it, and put the
    /// `Output` in the bus. Budget mode calls it once per step.
    fn mem_budget(bus: &MainBus, budget: &Budget);
}

impl MemBudget for ScfStep {
    fn mem_budget(bus: &MainBus, budget: &Budget) {
        let n = bus.dims.n_ao;
        let output = ScfOutput {
            c:   budget.device(Gpu(0), n * n),   // summed: later steps read it
            eps: budget.heap(n),                 // a fixed-size host slab
            ..
        };
        // Dies with the run: F, the DIIS ring, syevd's work. One region,
        // packed by the final node, lent to run by the layout.
        budget.scratch(Gpu(0), Kind::Device, ScfLayout::new(bus).bytes());
        budget.locks(&[Lock::Eri, Lock::AllGpus]);
        *bus.scf.write() = Some(output);
    }
}

What each Budget call for an Output does, in order:

  1. Add the bytes to the kind's atomic counter (per GPU for device and pinned) and to this step's row of the budget table.
  2. Check the counter against the cap. Over it: set the flag. Do not panic.
  3. Allocate, unless the flag is set.

A budget.scratch call only records a row (step, GPU, kind, bytes). The final node then packs each GPU and kind's rows into one slab (step scratch), adds each packed peak and the handle workspace to its counter, checks again, and holds heap and pinned against the host. If the flag is set it prints the whole table and exits. Otherwise it allocates the scratch slabs and each GPU's handle workspace, binds the latter to that GPU's BLAS handle once, records each step's offset, and logs the table.

  • Two modes, one run each. No counting run before an allocating one.
  • The same DAG, in parallel, with atomic counters. The total is order-independent, so accept or refuse is the same every run; deferring the exit to the final node makes the report the same every run too, complete and not whichever step crossed the line first.
  • Two moments of the device check: per step for Outputs, once at the end for the packed scratch and the handle workspace. Each is its own row.
  • In parallel pays on the host, where touching the pages of a multi-GB slab is the slow part.

What is budgeted, by kind

Kind Counter What Budget hands back Rule
Device Sum, per GPU A fixed-size device buffer An Output's: read by other steps, or carried over a replay
Pinned Sum, per GPU A fixed-size page-locked slab As device
Heap Sum, one for the host A HeapSlab<T> over a Box<[T]> Cannot grow; pages touched in mem_budget
Scratch Packed, per GPU and kind (device, pinned) A lease on the step's region for its run Packed and allocated by the final node; regions overlap only between steps the closure orders
Handle workspace A constant, per GPU Nothing: bound to the GPU's BLAS handle once 128 MiB, allocated by the final node

Host heap

  • A boxed slice, not a Vec. Box<[T]> has no push, reserve or extend, so "no growing" is the type's. HeapSlab is constructible only by Budget, which separates budgeted memory from an incidental Vec.
  • Touch the pages in mem_budget. Zeroed memory is handed out lazily on Linux; an untouched slab "succeeds" and fails at first touch mid-run, as a bare kill from the OOM killer.
  • The host is checked at every call, before the slab is allocated and touched, so a B larger than the host sets the flag and is never touched. The final node checks again with the packed pinned scratch added.
  • Not packed. The heap stays a sum. What a step's run needs on the heap and drops is small, or it is pinned staging, which is scratch.
  • Small host scratch is a policy, not a kind. A Vec or a HashMap that lives within a run is assumed small and is outside the budget: it stays within O(n_ao²), and anything larger is a HeapSlab on the MainBus. The allocation record checks it (enforcement), and the budget table prints execute mode's peak heap growth as an unbudgeted row.

Caps and margins

  • Caps come from the config, per kind. An explicit cap is used as written; the user owns the margin.
  • A defaulted device cap is the GPU's free memory at start, read once after its handles exist, less the margin: the larger of 512 MiB and 5% of the GPU's total memory.
  • A defaulted host cap is the host's available memory, read once in setup (cgroup-aware, fb_core_arena::host_available), less the larger of 1 GiB and 5%. With B on the host heap, this is the cap a large density-fitted run meets first.
  • Every cap is clamped to the reading. An explicit cap past the machine is clamped to the reading itself, no margin taken. The table prints the cap as written beside the value used. Without the clamp an impossible cap ends in an abort at whichever allocation fails first, or in the OOM killer.
  • The margins are judgment, not measurement. One too small costs a failed launch that says so (failure), and is raised then.

What the budget leaves out

For the user docs: the memory limits cover what steps allocate through mem_budget, step scratch (which holds every library call's work buffer), and the fixed handle workspace. They exclude the device context, the handles' own memory and loaded modules, the kernels' stack, and small host allocations such as reading the geometry and the basis data. A defaulted cap's margin covers those; an explicit cap is the user's.

  • The kernels' stack. CUDA holds a kernel's per-thread stack for every thread the GPU can keep resident (104,448 on the RTX 3080) from that kernel's first launch on. At the Rust-only kernels' largest frame, 3,856 bytes, that is about 280 MiB on the 3080. No row, no declaration. The risk is one loud failure: a plan that nearly fills the GPU fails at the first launch of a kernel with a larger frame than any before, in a named step, with an allocation error. Nothing budgeted can be in the way, since everything was allocated before the first launch. ROCm reserves nothing per frame (src/core/wwr/README.md, ROCm 7.2.4). Open: raise the stack limit at init, or budget the stack, once a kernel with a frame past 8 KiB is ported (the Hessian kernels).
  • Modules and a library's first call (2–10 MiB at a HIP solver handle's, up to 14 on cuSOLVER) are the margin's. No warm-up in budget mode. The handles themselves exist before the free-memory reading, so a defaulted cap already sees them.
  • No free-memory check at run time. Every vendor call measured to take memory by itself is no longer called (workspace), and the reading moves for reasons that are not the tree's (the stack, modules, other processes).

Lengths: counted in setup, built by the step

A kernel cannot walk a BasisSet. It reads flat arrays that say, for every unit of work, where its inputs are and where its result goes; the host builds them, stages them in pinned memory and uploads them. Records are data, one entry per primitive. Work lists are indices, one entry per unit of kernel work. Nothing in an entry is a pointer, so every array is sized by counting.

The density-fitting arrays on gly10 in cc-pVDZ / cc-pVDZ-JKFIT, unbatched (from v0.0.2/src/steps/eri.rs):

Array Kind One entry per Length, from Dims gly10
aux_records records aux primitive: x, y, z, α, c(π/α)3/2 5 × n_aux_prim f64 51 kB
metric_pairs work list aux shell pair P ≤ Q, by class (lP, lQ) 6 × n_aux_shell(n_aux_shell+1)/2 i32 19.4 MB
cells work list orbital shell pair × aux shell, by (orbital class, lP) 6 × n_shell_pair × n_aux_shell i32 1.79 GB
gather_at, gather_weight work list pair column: its μ and ν, and 1 or 2 2 × n_col i32, n_col f64 4.3 MB

Batched, cells is a pair batch's share, in the ERI buffer's ring.

  • Setup counts every length that scales; it builds none of those arrays. It has read the geometry and both bases, so it adds n_aux_prim, n_aux_shell, n_shell_pair and the per-class counts to Dims by a counting walk over the shells. The walk is the new layer's own: fb_integrals_mmd::record_tables builds every shell pair's bra, ket and record-prefix arrays to count from, which this rule forbids. Any array whose length scales with a pair count, or a product of shell counts, belongs to a step and is budgeted.
  • mem_budget charges, run builds. mem_budget declares the records and work lists as scratch, pinned and device, at their lengths from Dims. run builds them straight into its pinned region (a counting walk gives each class's offset, so no temporary Vec), uploads them on the step's stream, and launches.
  • A replay builds again, into the same regions. The records hold coordinates, which move; the lengths and offsets do not.
  • A refused or dry budget builds nothing and still prints exact lengths, since they are counts.

Step scratch

Memory a step needs during its run and nothing reads afterwards: a library call's work buffer, a solver's DIIS ring or subspace, build intermediates, the records and work lists. It is allocated in budget mode like everything else, since allocation in run is ruled out and a replay must allocate nothing. What lowers the peak is sharing scratch between steps, not releasing it: under the sum, a release frees bytes no admitted step can use.

  • Declared per step, packed by the closure. A step declares budget.scratch(gpu, kind, bytes) for device or pinned memory. The final node takes the transitive closure of the DAG (a bitset of successors per node) and packs each GPU and kind's rows into one slab: two steps' regions may overlap only if one reaches the other.
  • Largest first. First fit, by size then step id, each region at the lowest offset clear of every unordered region already placed. The offsets, and the table, are the same every run.
  • The table prints the lower bound and the steps that make it, beside the packed peak and the plain sum, so a config that packs badly shows itself. The bound is a floor, not a promise.
  • Safe whatever the packing's quality. Any placement that keeps unordered regions apart is safe; a poorer one costs bytes, and at worst a refusal at init, never a collision in a run.
  • Why the closure is enough. A finished node is finished device work (the wrapper's sync), so a path from A to B is a happens-before on the GPU as well as on the host, under any schedule the executor picks. Unordered steps never share. Two lock holders the DAG leaves unordered also keep their regions apart, though the lock serializes them: one safety argument, not two.
  • The step-end sync carries memory safety. Pinned scratch needs it whole: the host writes pinned bytes inside run, and the device reads them through copies done by the time the wrapper's sync returns. Event chaining would order device work along every path but not a host write after another step's copy. Any change to the sync is a change to this rule.
  • Computed once. The graph and every length are fixed, so the closure and the offsets are made once in budget mode. A replayed chain's closure is taken over one iteration of its body, laid flat into the outer DAG.
  • A condition's exclusive branches are packed as unordered: safe, at their sum rather than their max. Exclusive branches of the outer graph should be rare, since a config choice never enters the DAG and a runtime condition lives inside a step.
  • Addresses hold over a replay; contents do not. A step gets the same region on every run, and what is in it on entry is undefined. In a test mode the wrapper fills each lease with NaN before run.
  • One layout per step. A step's region holds several tenants (the SCF's: F, the DIIS ring, syevd's work). The layout is an associated type of the step: mem_budget declares its total and the wrapper carves the lease by it, once.
  • A lease cannot escape. It borrows for the length of run, so a step cannot store its scratch in its Output. The overlapping slices need one unsafe, in the arena, with the closure invariant beside it.
  • Inner tasks split their step's region themselves. The closure is over the outer graph only.
  • Bytes in place of time. No lock, so a scratch user never waits on another for memory.

Batched only

Every step over an O(N³) tensor has a batched path and no other. The unbatched case is the batched one with a single batch on a single GPU.

What a step holds Rule
Everything O(N²): the n_ao² matrices, the metric and its factor, the records Resident whole on the GPUs it needs. It fits or the plan is refused: a dense eigensolve at n_ao cannot be batched
The O(N³) tensors: (μν|P), B, a derivative of B Never resident whole. Built or contracted a batch at a time; B itself on the host heap
The batch width The widest whose bytes fit the step limit; none fits: refuse, naming the step, its limit and its least bytes
The step limit Covers the batch, the ring and the cache, not the O(N²) residents, which the cap admits or refuses. A fixed constant by default; the config overrides it, which is also how a test forces many batches on a small molecule
What is charged What is used, never the limit. Limits need not sum to the cap
  • Every GPU step is built batched and for every GPU, or not built. A feature is not added until it runs on a single node's num_gpus GPUs, one GPU being the case of one.
  • Width stops mattering early. In df_batched/single_gpu the build's time is flat past about 20 batches, and width 1 costs 5.6× to 11.6×.
  • No "what is left". A width is a function of the step's own limit, so mem_budget stays local and order-free.
  • A width of one is logged at warn; the user raises the limit.
  • Sizes fixed only by an earlier step's run (the screened pair count, the orbital count after dropping linear dependencies) are allocated at the bound Dims gives. The pair count's bound is the count in the tree's own pair layout (270,497 pair columns on gly10, where n_ao(n_ao+1)/2 gives 269,745). On a large sparse molecule that wastes host memory, and a replay can never outgrow its buffers.
  • Out of scope: AVAS, the semi-numerical Hessian, semi-numerical gradients.

What can still be refused: a plan whose O(N²) data does not fit its GPUs, whose B does not fit the host, whose step limit holds no batch, or whose Outputs, each fitting alone, do not fit summed down a chain. The last is the sum's price; the remedy is a narrower batch in the step concerned.

GPUs, streams and locks

Which GPUs a step runs on

num_gpus comes from the config. A step runs on no GPU, on gpu0, or on all of them; no step runs on GPU k alone or on some of them. The assignment is fixed when the DAG is built, before budget mode, since mem_budget must know which counters to charge.

  • gpu0 is the privileged GPU. A one-GPU step runs there, and dense diagonalization is single-GPU.
  • An all-GPU step splits its data across every GPU and reduces its results onto gpu0. A step that calls an all-GPU method is an all-GPU step (the SCF, through build_jk), though its eigensolve runs on gpu0.
  • A device buffer is on gpu0 or on every GPU, as the Budget call that allocates it says. gpu0's cap is the one that binds.
  • With one GPU, all is gpu0. Not a second path.
  • The current device. Launches and library calls run on the calling thread's current device. The wrapper makes the step's device current for the body, and every inner task that launches does the same with a ScopedDeviceIndex, since a stolen task runs on whatever thread is free.
  • Host steps relieve gpu0. The one-electron matrices and the metric are computed on the host on rayon's threads (s_overlap_host, t_kinetic_host, v_potential_en_host, df_metric: on gly10, tens of milliseconds) and uploaded. An upload calls no library, so these steps take no lock and run beside the GPU work.

Streams

A GPU step has streams of its own on each GPU it spans, one by default, more if declared. The wrapper makes them in budget mode and keeps them in the step's slot, beside its Output. A step's kernels and copies go there.

  • run enqueues; the wrapper syncs. The DAG builder wraps every GPU step's run in one generic function: make the device current, take the step's declared locks, call run, synchronize every stream the step has and each held GPU's stream, then release the locks. A step cannot skip it.
  • Whoever fans out, joins. A step's inner tasks, and a manager method's fan-out across GPUs, are finished before run returns. The wrapper's sync is the last word, not the only one.
  • A finished node is finished device work, on every stream the step touched. So the DAG's edges order everything between steps, with no event between steps, and any worker can run any step. Steps that call no library overlap on a GPU for free.
  • The sync blocks, so the waiting thread sleeps. A waiting worker is not stealing, so the executor's width covers the GPU steps that can wait at once, plus the CPU work: a handful of threads.
  • Two thread pools. The host integrals run on rayon's threads, called from a step on a rustflow worker; each pool has its own thread count from the config.

One handle set per GPU, under its lock

Each GPU's GpuResources is a Mutex around that GPU's stream, a BLAS handle and a dense-solver handle made on that stream, and the 128 MiB handle workspace. The handles keep that stream for the life of the process: SetStream is never called after creation, and the workspace is bound once.

  • A library-using step declares the GPUs it calls the library on, in mem_budget, and its library calls go on those GPUs' streams. A simple library user (the orthogonalizer) puts everything there, in the order it enqueues, with no event.
  • The handles are reachable only through the guard. "No handle is shared with work in flight" is the borrow checker's: the previous holder synced the GPU's stream before releasing.

  • A step's inner tasks share its handle set. An inner task for a GPU takes that GPU's guard from the step, mutably. A step that wants concurrent library calls inside itself declares further handles of its own, with budgeted workspaces.
  • What it costs: library-using steps are serial on a GPU, whatever the DAG says, because the lock is held for a whole run. A long one serializes every short one behind it. Heavy steps fill a GPU on their own anyway, and two on one GPU time-slice rather than overlap (a CASSCF case measured 2.3 s alone and 158 s beside the exchange build, in this tree's test batches).
  • A handle set is not free: about 20 MiB on CUDA and 52 on HIP (handle_ring). One per GPU is the floor.

Lock order

There are two kinds of lock: one per manager (here only the EriManager's), and one per GPU. A deadlock needs a cycle: one step holding the manager and waiting for gpu1 while another holds gpu1 and waits for the manager. The rule that makes a cycle impossible:

  1. One global rank: every manager first, by a fixed id, then the GPUs by index: enum LockId { Manager(ManagerId), Gpu(usize) }, with Ord derived in that order.
  2. A step declares every lock it takes in mem_budget, beside its scratch.
  3. The wrapper takes the declared set in rank order before run, and releases it after the sync.
  4. Nothing takes a lock inside run.

If every step takes its locks in increasing rank, nothing can hold a higher lock while waiting for a lower one, so no cycle forms. Rule 4 is held by type: run never sees the MainBus, so it never sees a Mutex. It receives the guards already held:

// scf declared {Eri, gpu0, gpu1}; the wrapper locked them in that order
fn run(view: ScfView<'_>, held: &mut Held<'_>, lease: Lease<'_, ScfLayout>) {
    view.eri.build_jk(held, &d, &mut j, &mut k);
}

build_jk takes the GPU guards as an argument; the manager has no path to a GPU's Mutex, so it cannot lock on its own. The same rank keeps collectives issued in the same order on every rank. A step re-run by a condition loop takes its locks each time.

A step with streams of its own and library calls

eri is the case (df_batched/multi_gpu_spherical builds it): each GPU builds its share of B over a ring of two pair batches, and every batch has kernels, a library fit and a download.

  • Each ring buffer has a stream of its own, carrying its batch's upload, its three-centre kernels and its download.
  • The fit goes on the GPU's stream. It waits on the event its ring stream recorded after its kernels, and the download waits on the event recorded after the fit.
  • The host waits on a ring buffer's last event, not a whole stream, before it scatters that batch into B and writes the buffer's pinned bytes again.
  • The metric's factor is on the GPU's stream before the loop, and overlaps the first batch's kernels.
  • Two fits never overlap on one GPU; the ring overlaps a batch's copies and kernels with the previous batch's fit.
  • The events are the step's own fan-out, all waited on before run returns.

Failure, diagnostics, determinism

  • A plan over budget is a refusal, not a panic: the final node prints the table and exits with an error. An allocation the counter admitted and the device refused aborts at the failing call, still at init.
  • A launch that fails for memory reports what it can read. By execute mode everything budgeted is allocated, so the failure is about memory outside the budget. The error names the step and the kernel, prints the GPU's free memory and, on CUDA, the stack limit, lists the causes on that backend (a larger frame than any before, modules loading, another process), and suggests a lower device cap.
  • A config whose steps do not close is refused when the DAG is built, naming the step and what it needs.
  • A step's failure in execute mode is a Result. A failed step fails its successors and nothing else: the wrapper holds a failed flag per node. A panic surfaces from wait as RunError::Panicked.
  • The budget table is the memory diagnostic: one row per step and kind, the ERI buffer and the handle workspace their own rows, the packed scratch beside the plain sum and the lower bound, the totals against the caps, each cap as written beside the value used. rustflow's ChromeObserver and dump() sit beside it.
  • Determinism. Results are those of the edges. Accept or refuse, the scratch offsets and the table are the same every run; the order steps were budgeted in is not.

How it maps onto this design

  • The top three levels are setup. The reads, the electron count, the nuclear repulsion and the two basis sets are small host work, unbudgeted, and they fill Dims. Budget mode starts below them.
  • The one-electron matrices and the metric are host steps. S, T and (P|Q) are built directly in the solid harmonics on rayon's threads; V turns each contracted shell pair's Cartesian block spherical through the harmonics' nonzeros, so no Cartesian matrix exists and no spherical transform is a node. They are uploaded: S and H to gpu0, the metric to every GPU. They take no lock and overlap the GPU work.
  • Three steps hold gpu0's lock: the orthogonalizer (an eigensolve), eri (the factor and the fits, on every GPU) and the SCF. The orthogonalizer and eri are unordered, so one waits for the other.
  • The factor, (μν|P) and B are one step, eri, whose Output is the EriManager. (μν|P) exists only a pair batch at a time, in the ERI buffer's ring; B is on the host heap.
  • Scratch is packed. The orthogonalizer's eigensolve work and eri's records are unordered, so their regions are disjoint; the SCF follows both and may reuse either.
  • The peak moved off the GPU. B's 7.80 GB slab is on the host. A GPU holds its O(N²) data, the metric and its factor (0.21 GB), the ERI buffer and the handle workspace. Unbatched, gpu0 held B, and the 1.79 GB cells work list on each side: 9.86 GB of device memory in all.

Choices the graph leaves open

  • How (P|Q) is orthogonalized: a Cholesky factor and a triangular solve, as drawn, or a symmetric J−1/2 that can drop near-dependent fitting functions.
  • How X is built: symmetric S−1/2, or canonical, which may give fewer orbitals than basis functions.
  • Which initial guess: a superposition of atomic densities read from a table, as drawn; a core-Hamiltonian guess would depend on H, X and the electron count.
  • What the screening map bounds: the Schwarz bound over orbital shell pairs, as drawn; one that also uses √(P|P) adds an edge from the auxiliary set.

Symmetry, frozen orbitals and effective core potentials are left out; none changes the shape.

Open questions

To discuss

  • Several nodes. The commitment is to one node's GPUs. Keeping several nodes open cheaply is one rule: work on different GPUs communicates only through the collectives layer. B on one host's heap is the first thing that rule would have to answer.
  • Packing Outputs too, by the same closure from producer to last reader, once the measurement says Outputs are what stacks.
  • What is cleared between replays, and by whom: a reset mode per step (as built), an explicit on_replay, or a node at the loop's entry or end.
  • rustflow and doc_check's thread-pool rule. rustflow depends on crossbeam-deque, which rust/docs/programming_model.md ("CPU workers") forbids any member to reach. The first member of rust/ on rustflow changes that rule with it; a prototype that is a Cargo workspace of its own needs no change.

To measure, verify or pick a value for

  • The default step limit for eri: the value in place of the 2 GiB placeholder; the threshold of the allocation record.
  • The blocking sync: which scheduling flag makes a waiting worker sleep, on each backend, and what the sync costs per SCF iteration.
  • The executor's width against the GPU steps that can wait at once, on a sync or a lock.
  • What the sum costs: per examples/ config, the summed step peaks against the fold, split into Output and scratch bytes, and whether the peak is inside one step or across many.
  • Packing quality on real configs: the table's lower-bound row answers it on each.
  • The rest of the workspace sweep: upper solves, rectangular syrk and gemv, the batched solver calls, hipBLASLt. What the sentinel tests would run.
  • Scratch on HIP while a kernel runs, on ROCm 10, sampled during a large launch: the HIP share of the device margin.
  • Task granularity inside a step: how much of its inner graph is rustflow's and how much a plain loop on one stream.
  • The cells work list as a kernel's own: a dense cross product a kernel could derive from two short lists (58,653 and 1,272 entries on gly10), a FelizJueves change. It lowers the ERI buffer a batch needs.
  • Rebuilding only the records on a replay, if the full rebuild costs.
  • Collectives: whether NCCL and RCCL mind a rank moving between steps' streams.
  • Idle workers: what rustflow's parking costs while a run waits on the device (src/executor/notifier.rs; verify).
  • Pinned pages and NUMA: a pinned slab is touched by whichever worker runs its step's mem_budget.
  • cuBLAS and rocBLAS handle thread-safety: the lock answers it either way; verify what each documents.
