# CLAUDE.md

## What this is

free-breakfast is a GPU-first scientific computing project in C++23 named
modules, targeting **either CUDA or HIP** from one source tree. `test/pytest/`
and `devtools/` are a Python tooling layer around it, not a shippable package.

It is an early quantum-chemistry codebase. `src/` holds fourteen modules: `core`
(the GPU, error-handling and logging vocabulary over WarpWraps), `atom`,
`molecule`, `basis`, `io`, `sad` (the SAD initial guess), `recipes` (dense
GPU linear algebra), `integrals` (GPU integrals over kernels generated by
the FelizJueves submodule, integral-direct and density-fitted), `localization`
(Pipek-Mezey orbital localization, IBOs and LIVVOs), `analysis` (IAO
populations and partial charges), `ci` (determinant CI: strings, sigma, the
solver and RDMs), `response` (the CASSCF energy, orbital gradient and
orbital Hessian at fixed orbitals and RDMs), `mcscf` (the state-averaged
CASSCF loop over them) and `pipeline` (the calculation pipeline: the step
contract, the setup steps, the ERI step (integral-direct or density-fitted,
built once for every reader), the RHF SCF, the localization step, the active-space, CASCI, FCI and CASSCF steps, and the
planner that runs them from a TOML config). `src/README.md` has the one-line summary of each.
The build system, containers, tooling and CI around them are real and exercised.

## Setup

```bash
git submodule update --init --recursive   # REQUIRED -- nothing configures without it
uv sync                                   # creates .venv from uv.lock
pre-commit install                        # commit-time lint + pre-push gate
devtools/devcontainer.sh rebuild          # the C++ toolchain lives in here
```

`uv` is the only assumed host tool. **`uv.lock` is tracked, and it is the only
place Python dependency versions are written down:** `pyproject.toml` says what
is wanted, the lock says which exact versions satisfy it, and
`Dockerfile.base`'s `uv sync --frozen` installs that same lock — so the
container and the host cannot drift. After editing `pyproject.toml`, run
`uv lock` and commit the result. Do not hand-install with `uv pip install`.

`devtools/doctor.sh` reports what is degraded. Run it first when something
behaves oddly — **and run it on both sides**, because this repo has a host half
and a container half and doctor is what tells you which one you are on. On a
bare host, ~11 warnings (the whole C++ toolchain and the three `/opt` trees) is
the expected healthy state, not a broken machine.

On the host it also answers a question no test run can: its `gpu kernel
modules` section asks whether each vendor's **DKMS** module is built for the
kernel the *next reboot* will pick, not just the running one. Both drivers here
are out-of-tree, a failed per-kernel rebuild is silent, and the card is lost at
the reboot rather than at the upgrade — so a warning there means *do not reboot
until it is fixed*. It is the host-side half of the GPU plumbing; the
container-side half is the `--device=` lines in `.devcontainer/*/`.

Doctor resolves the tools it reports through `VENV_PATHS`, not `PATH` — the
cmakelang pair lives in `.venv/bin` on the host and `/opt/venv/bin` in the
image, and a bare `command -v` called them missing on the host while passing in
the container.

## The three dependency worlds

They are wired differently and the difference matters.

| World | Where | How it arrives |
| --- | --- | --- |
| **WarpWraps** | `deps/WarpWraps` | git submodule, built from source as part of this build |
| **Prebuilt C++** | `/opt/{spdlog,taskflow,tomlplusplus}` | compiled into the image by `docker/Dockerfile.base`; `find_package` |
| **Python** | `.venv` / `/opt/venv` | `uv sync --frozen` from `uv.lock` |

Plus `nlohmann_json`, which is FetchContent because it is header-only and small.
And `deps/FelizJueves`, a submodule that is **not built**: it is the Python
generator `tools/emit/one_electron_kernels.py`,
`tools/emit/coulomb_kernels.py`, `tools/emit/exchange_kernels.py` and
`tools/emit/df_kernels.py` run by
hand, their kernels committed under `src/integrals/`; re-run all four after
bumping it. The build takes only its `include/`, as the
INTERFACE target `felizjueves::headers` (`deps/CMakeLists.txt`): the
vendor-neutral `felizjueves/runtime.h` every generated kernel includes, with
`FJ_WAVEFRONT` mirrored from `WWR_WARP_SIZE`.

**WarpWraps is the GPU API layer, and this project does not duplicate it.**
There is no `deps/cuda/` of hand-written `cuda_runtime_api.cppm` /
`cublas_v2.cppm` shims here; that is exactly what wwr's `src/cuda` (and its
`src/hip` mirror) is, and an earlier ancestor of this tree carried a narrower
CUDA-only copy of it.

**Inside `src/`, wwr is reached through `free_breakfast.core.wwr`**
(`src/core/wwr`, target `free_breakfast::core::wwr`): import that, not `wwr.*`,
and link it, not `wwr::*`. It re-exports every wwr module the tree uses, plus
`gpu_status`, the GPU error policies, and the wrappers bound to them. To use a
new wwr module, add it there. The exceptions, which link wwr directly, are
`core/types` (it sits below the error layer `core.wwr` is built on),
`core/constants` (its `constants.h` is shared with device code, so it includes
wwr's `complex.h` rather than importing), header
and `.cu` device code (`wwr::device`; nvcc cannot import), and a deliberately
CUDA-only `import wwr.cuda.*`. `src/core/wwr/README.md` has the reasons.

**GoogleTest comes from WarpWraps too**, not from this tree. wwr's own `deps/`
declares it, and FetchContent is first-declaration-wins, so declaring a second
one here would not give this project a different GoogleTest — it would only make
the pin look like it lived here.

### wwr's own tests are switched off

`deps/CMakeLists.txt` adds it with `add_subdirectory` and sets
`WWR_BUILD_TESTS` and `WWR_BUILD_EXAMPLES` **OFF** (both already default OFF
for a nested build; they are set explicitly so this does not depend on a
default staying put. `WWR_INSTALL` shares that nested default, but this build
forces it **ON**). So wwr calls no `enable_testing()`, adds
no `test/` or `example/` directory, and a top-level `ctest` lists only this
project's entries. wwr's suites are wwr's CI's job, not this tree's.

GoogleTest is **not** behind those switches — wwr's `deps/` is gated only by
`WWR_COMPILE_TIME_ONLY` — which is what keeps the `GTest::*` targets this
project's tests link.

Coverage still excludes `/deps/` (`COVERAGE_IGNORE_REGEX` in
`devtools/config.sh`): wwr's libraries and GoogleTest are still compiled into
this build.

`enable_testing()` is still called before `add_subdirectory(deps)`. CMake
writes a `subdirs(...)` line into a directory's `CTestTestfile.cmake` only if
testing was enabled when that directory was *processed*, so a directory added
above the call has its tests silently dropped — the same trap the
`experimental/` guard at the bottom of the root `CMakeLists.txt` documents.
Keeping the call first means every directory gets the same treatment.

## The backend switch, and why it is before `project()`

`FREE_BREAKFAST_GPU_BACKEND` is `CUDA` or `HIP`, and a build is exactly one of
them. It is read **before `project()`** because it decides whether the CUDA
language is enabled at all — and it has **no default** for the same reason: a
silent one would quietly require a CUDA toolkit on a HIP-only host, or ROCm on a
CUDA-only one. Every preset carries it.

The root `CMakeLists.txt` mirrors it onto `WWR_GPU_BACKEND` (and
`FREE_BREAKFAST_COMPILE_TIME_ONLY` onto `WWR_COMPILE_TIME_ONLY`) before the
subdirectory is added. **Do not set either `WWR_*` variable anywhere else.** A
tree built CUDA against a HIP wwr fails deep inside wwr's own sources with
nothing naming the mismatch.

**The architecture floor is sm_80, and it is WarpWraps' floor, not the
toolkit's.** wwr wraps bf16 tensor-core WMMA (Ampere), so it rejects a sub-80
`CMAKE_CUDA_ARCHITECTURES` at configure. CUDA 13's own nvcc floor is lower
(`compute_75`) but never binds. The root CMakeLists checks it too, so the error
names this project. Keep `CUDA_ARCH` in `docker/Dockerfile.cuda` at 80+.

## Sanitizers: two options that are easy to get silently wrong

**`compute-sanitizer` the preset is only a Debug build.** What wraps the tests
is `FREE_BREAKFAST_COMPUTE_SANITIZER_TOOL` (empty by default), which sets
`CMAKE_TEST_LAUNCHER` so it covers every test target in the tree (and would
cover wwr's too, were `WWR_BUILD_TESTS` ever turned on). It
must be set before the test targets are created — CMake snapshots it onto each
target as `TEST_LAUNCHER` at creation time — which is why it lives near the top
of the root `CMakeLists.txt` and not beside `add_subdirectory(test)`.

`docker/compose.yaml`'s `compute-sanitizer` service passes it, and before the
option existed that `-D` was accepted and ignored: the service built, ran plain
ctest, and reported success having checked nothing. If you add another `-D` that compose passes,
check the option actually exists.

`--error-exitcode=1` is load-bearing: compute-sanitizer exits 0 by default even
when it reports errors.

**ASan needs `ASAN_OPTIONS=protect_shadow_gap=0`.** Not tuning — ASan's reserved
shadow gap collides with the GPU driver's virtual-address reservation, and the
first device allocation then fails as `cudaErrorMemoryAllocation` on a card with
plenty of free memory. It is set in the `asan`/`hip-asan` *test* presets (so
`cpp-tier.sh --preset asan` works) and separately in compose's `asan` service,
because compose runs bare `ctest --test-dir` and never sees a test preset. Both
copies are deliberate; keep them in step.

## Basis sets are build input, not installed data

`data/basis/*.json` is BSE JSON downloaded by `tools/basis/bse_download.py` and
**compiled into the binary**: `src/io/basis/CMakeLists.txt` wraps each file
verbatim in a raw string literal in a module implementation unit generated from
`builtin_basis.cpp.in`, and `resolve_basis("sto-3g")` parses it out of the
binary. This tree installs nothing of its own, so the alternative — a runtime
data directory — would mean inventing an install rule and a search path that
can work on one machine and not the next.

`resolve_basis` takes a **name or a path**, name first, so a basis the build
does not carry is still read from disk with no rebuild. That escape hatch is
what keeps baking from being a restriction, and it is why
`BasisSetStep::basis` is a `std::string` rather than a path: only
`pipeline/config` knows which of the two it has, via `is_builtin_basis`, and a
name must not be joined to the config file's directory.

**Only spherical sets can be carried.** `src/io/basis` rejects
`gto_cartesian` at any l by design, and `parse_basis` walks the whole
document, so one Cartesian shell anywhere makes the entire file unreadable.
The Pople sets' d shells are Cartesian (6-31G's from K up, 6-31G* and
6-31G**'s from Li), so all three are carried relabelled spherical (5D) by
`tools/basis/cartesian_to_spherical.py` — different bases from BSE's 6D ones,
by decision. Check the harmonic types before adding a set; `data/basis/README.md`
has the detail and the regeneration commands.

**So are the SAD stamps.** `data/sad/<basis>/<Z>.npy` is every element's atomic
density in every carried set, written by the C++ generator `tools/sad`
(`free-breakfast-sad-stamps`, built with the tree) and compiled in by
`src/io/sad` the same way. Each 3d element's SCF takes minutes in cc-pVDZ/TZ.
The Guess step takes a stamp only for a basis whose `BasisSet::name()` is set,
and only `resolve_basis`'s compiled-in branch sets it. A path-read basis
computes every element, even if its document claims a carried name. **Changing
`data/basis/` or the atomic SCF means regenerating `data/sad/`**; the bitwise
check in `test/io/sad_host.cpp` fails until you do. The commands are in
`data/sad/README.md`.

## The two languages, and what verifies which

| | C++ | Python |
|---|---|---|
| Source | `src/`, `cmake/`, `deps/` (+ opt-in `bench/`, `experimental/`) | `test/pytest/`, `devtools/hooks/*.py`, `tools/` |
| Tests | `test/core/` (the `src/core` tests) and `test/gtest/` (the rest), each a host/GPU binary pair, and `test/basis/` (the host-only `src/basis` tests), `test/io/` (the host-only `src/io` tests) and `test/pipeline/` (the `src/pipeline` tests that need no device), each a host binary, run by ctest | `test/pytest/`, run by pytest |
| Driver | `devtools/cpp-tier.sh`, `cpp-slow-tier.sh` | `pytest`, `devtools/slow-tier.sh` |
| Lint | `cmake-lint`, `clang-format --check` (commit hook + CI); `clang-tidy` via `--tidy` | `ruff check`, `ruff format --check` (commit hook + CI) |
| Gated by | `cmake-lint` + format check at commit, `cpp-smoke.sh` at push; on the server **format + cmake-lint only, no build or test** | pre-push hook + CI |

**A change under `src/` is verified by the C++ tier and by nothing else.** A
green pytest run on it means the Python that would have exercised the *old*
binary still imports. Say which suite you ran.

`clang-tidy` is configured and runnable (`devtools/cpp-tier.sh --tidy`) but is
**advisory, not a gate**, and off by default: its C++23 named-module support is
still incomplete enough to emit bogus diagnostics on a `.cppm`. Do not bend the
module hierarchy to satisfy it.

### What is gated, and what is not

`git push` runs the fast pytest tier when the push touches a `.py`, and
`devtools/cpp-smoke.sh` when it touches C++. CI runs lint + the fast pytest
tier per PR.

**The `cpp` job in `.github/workflows/ci.yml` is `if: false`** — both matrix
legs, cuda and hip. A PR touching only `src/` gets its formatting and CMake lint
checked on the server and nothing else: nothing builds or runs it.
`devtools/cpp-tier.sh` before opening it is the whole correctness gate, and it
is a human one. The `ci-cuda` and
`ci-hip` presets were built for that job and need **no GPU** — the only obstacle
is getting the toolchain image onto a runner, and that file's comment has the
two routes.

## Containers: four files, two front ends

`docker/Dockerfile.{base,cuda,hip,combined}` is a diamond, and the four
**chain by tag, not by stage**: each child opens `FROM ${PARENT_IMAGE}`, so the
parent must be built and tagged first. `docker/build.sh <target>` walks the
chain. Building a child by hand with no parent tagged does not fall back to
building one — it tries to *pull*, and fails with `pull access denied for
free-breakfast`, which reads like a registry problem.

`combined` is the bottom of the diamond in intent only: docker has no multiple
inheritance, so it takes `cuda` as its parent and **re-runs**
`docker/install-rocm.sh`. That is why that block is a script rather than an
inline `RUN`.

Two front ends onto the same image:

- **`docker/compose.yaml`** — the batch path. `build` / `test` / `asan` /
  `compute-sanitizer`, each one-shot, teeing to `.log/`. Requires
  `HOST_UID`/`HOST_GID` in the environment (`:?`, not a default, so a forgotten
  export fails loudly instead of writing root-owned files).
- **`.devcontainer/{cuda,hip,combined}/`** driven by
  `devtools/devcontainer.sh` — the interactive path, per worktree, with its own
  container, volumes and CPU bounds. Pick a variant with `--cuda`/`--hip`/
  `--combined`, or `DEVCONTAINER_CONFIG`.

**They do not share a build directory, and cannot.** The devcontainer mounts the
workspace at its *host* path; compose mounts it at `/workspace`. A CMake cache
records absolute source and binary directories, so a tree configured by one
front end is rejected by the other with `The current CMakeCache.txt directory
... is different than the directory ... where CMakeCache.txt was created`.
Caches are not relocatable, so compose configures with `-B $BUILD_DIR` into its
own `build-compose*/` rather than the preset's default.

**Use `rebuild`, not `up`, after editing a `Dockerfile` or `devcontainer.json`.**
`up` reuses the running container, applies none of the change, and reports
success with the same container id.

### The duplication that is load-bearing

`PROJECT_NAME` in `devtools/config.sh` and the volume/container names in the
three `.devcontainer/*/devcontainer.json` files **must agree**, because JSON
cannot source shell. It is `free-breakfast` — the hyphenated spelling — in both
places, while the C++ namespace and CMake targets use `free_breakfast`. Get this
wrong and `worktree.sh rm`/`gc` stop recognising this project's volumes as its
own. `doctor.sh` checks that each file's volume `source=` names carry
`PROJECT_NAME` and warns when they have drifted; it prints one `ok` line per
variant. It does not check the container `name` field.

## Reading a test run

**A green run means nothing until you know what skipped.**

- C++ GPU cases call `FBF_REQUIRE_GPU()` (see
  `test/support/gpu_requirement.h`) and `GTEST_SKIP` with a reason rather than
  failing, so the suite stays usable on a device-less host. Read the skip
  lists: ctest's `***Skipped`, and gtest's `[  SKIPPED ]` in the `[gpu]`
  summary that `cpp-smoke.sh` and `cpp-tier.sh` print.
- Python: always pass `-rs`. Without it the suite looks identical on a GPU box
  and a laptop.
- `FREE_BREAKFAST_FAST_TESTS` makes `slow_test.h`'s macro skip the heavy
  validation cases. `cpp-tier.sh` and `cpp-smoke.sh` set it;
  `cpp-slow-tier.sh` is the un-skipped run.
- **A card can be enumerated and still run nothing**, in which case every GPU
  case skips and ctest prints `100% passed`. The AMD one wedges with `amdgpu`
  still bound and the KFD node still listing it, while HIP returns
  `hipErrorNoDevice`; `devtools/doctor.sh`'s `gpu devices` section reads the
  PCI device's runtime-PM state and warns rather than reporting the card `ok`,
  on both sides of the host/container split. The cause is host-side (a reboot
  fixes it), so believe doctor over the enumeration.
- **A card can also wedge mid-run** (gfx1200, #477): every process on it
  spins in a HIP sync and prints nothing. The GPU batch of `cpp-tier.sh` and
  `cpp-smoke.sh` is watched for that (`GPU_BATCH_STALL_SECONDS` and
  `GPU_BATCH_BUDGET_SECONDS` in `devtools/config.sh`): a silent batch is
  killed and the line `[gpu] hung in <case>` names where. When the same gate
  hangs in a different case each time, suspect the card before the case, and
  rerun the gate on the other backend. Before the kill the watchdog writes the
  batch's state (vendor tools, a rocgdb backtrace of every thread) beside the
  tier's log, as `<log>.gpu-wedge.txt`, and the `state before the kill:` line
  names it —
  attach it to #477, with the host's `dmesg` it ends by asking for.

Tests are registered **one ctest entry per gtest case** via
`gtest_discover_tests(… DISCOVERY_MODE PRE_TEST)`. `PRE_TEST` defers enumeration
to the start of the ctest run on the machine that will run the tests, and
`--gtest_list_tests` only walks the registry so it never initialises the GPU
runtime. A single `add_test` entry instead would make `ctest -R` select nothing
while still reporting success, and `1 of 1 passed` would read identically
whether every case ran or most of them skipped.

**`cpp-tier.sh` does not run every entry as its own process, though.** A GPU
process spends about 0.45s creating the runtime's context before its case
starts, which was most of the tier's wall clock. So it lists the entries
(`ctest --show-only=json-v1`, so the preset's filters and `-- -R …` still
select), and `devtools/split-gpu-entries.py` takes out the GPU ones that can
share a process. Those run as one gtest process per GPU binary
(`free_breakfast_core_tests_gpu`, then `free_breakfast_tests_gpu`), one after
the other and never at once, as in `cpp-smoke.sh`. ctest runs the rest,
`CTEST_JOBS` at once: the host entries, the `RUN_SERIAL` cases it keeps alone
on the card, and every entry when a launcher such as compute-sanitizer wraps
them. So its ctest summary counts only those, and each batch reports in its own
`--- gpu batch` and `[gpu]` lines below it: read both. `cpp-slow-tier.sh` still
runs plain ctest.

**One process, not shards.** Processes on one card time-slice it, and a
latency-bound case (a CASSCF's thousands of tiny synchronised launches) waits
behind its neighbours' long kernels: `PipelineNevpt2.PcRefusalKeepsSc` is
2.3s alone and 158s beside two `F/ExchangeGolden` processes. Shards bought no
wall clock on either card (`devtools/config.sh` has the numbers) and made
every per-case time in a log unreadable, so the times in a `[gpu]` log are
what `slow_test.h`'s rule is applied to.

**Both PR gates have a budget: under five minutes on a busy card.** Those are
`cpp-smoke.sh` at push and `cpp-tier.sh` before a PR. `test/support/slow_test.h`
has the rule that keeps them inside it: a case past about ten seconds goes
under `FBF_SKIP_IF_FAST_TESTS()` unless it is its family's cheapest.

### The one portability hole no tier sees

Every tier builds exactly one backend. A `.cu` goes through **nvcc** under CUDA
and **clang `-x hip`** under HIP, and nvcc is the more permissive of the two — a
functor holding a `const` member of class type passes the entire CUDA tier and
only breaks on a ROCm build. `devtools/cross-backend-check.sh` is the
seconds-long answer; run it whenever a change touches a `.cu`. It exits **2**,
not 0, when it cannot run, so a skip is never mistaken for a pass.

### What a tier cannot tell you about one kernel: how long it took to compile

`cmake --build` reports a target, not a file, so one emitted kernel that takes
an hour in the back end looks like a build that hung — no file named, and no
way to know whether it will ever land. The cost is not linear in the class
either, and the source size does not order it. `devtools/kernel-compile-watchdog.sh`
compiles each matching kernel **on its own**, deleting the object first so the
number is real, under a per-file `timeout` (`--limit`, 300s by default), and
prints every time with the slowest ten. Run it after `tools/emit/*.py` or a
`deps/FelizJueves` bump, narrowed to what you touched:

```bash
devtools/kernel-compile-watchdog.sh 'density_fitting/.*kernels/'
```

It exits 1 when a kernel goes over or breaks and **2** when it could not run
at all. Like the cross-backend check it is one backend's answer, and not a
hook: a full ladder is minutes of compiler time, the slow tier's budget.

## Conventions worth not rediscovering

- **`IMPORT_STD` is not bookkeeping.** A module library that says `import std;`
  without it is not built with `CXX_MODULE_STD`, and the failure names the
  standard library rather than the flag.
- **A `.cu` never goes into a test executable or a module library.** Those are
  scanned for modules (and, with `IMPORT_STD`, built with `CXX_MODULE_STD`),
  and nvcc neither
  understands `import std` nor participates in module dependency scanning. Put
  device code in its own `free_breakfast_add_gpu_device_library` target.
- **`hip::device` is always PRIVATE**, never PUBLIC or INTERFACE: its `-x hip`
  must reach one library's own sources and nothing else. A consumer picking it
  up transitively starts compiling its plain C++ as HIP.
- **Link the `::` alias, not the dotted target name.** The alias makes a typo a
  configure error.
- **Style is `docs/style.md`; read it before writing C++.** The format is
  *checked*, never applied, by a hook: `devtools/format.sh --check`
  (clang-format + ruff format, pinned by `uv.lock`) runs at commit and in CI's
  `lint` job; `devtools/format.sh` fixes. `cmake-lint` holds CMake to 80
  columns. Constants are `kCamelCase`.
- **Look in `src/core/` before writing a helper or a constant.** Don't re-derive
  or rename what is already there. A block is `kFourWarps`, not a per-file
  `kCiBlock = kFourWarps`, and a block count is `math::idivup`, not
  `(n + b - 1) / b`. `src/core/README.md` lists each directory's names, and
  `docs/style.md` "Launch shape and integer rounding" has the rule.
- **No anonymous namespaces, no `detail` namespaces** — except anonymous
  namespaces in `.cu`, `test/gtest/*.cpp`, `test/core/*.cpp`, `test/io/*.cpp`, `test/pipeline/*.cpp` and the `main.cpp` of `src/` and
  `tools/*/`, which are not module units. In a
  module, not exporting *is* the privacy; module-private code shared between
  units goes in a partition. `docs/style.md` "Module-private code" says which
  kind, and why an unexported name must still be unique module-wide.
- **A failed GPU create/alloc aborts, in every build.** The wwr wrappers'
  creation slots use free_breakfast's own `AbortPolicy` (via `CreatePolicy`: log
  critical, `std::abort()` at the failing call); destroy/free slots use its
  `LogPolicy` (via `DestroyPolicy`). Both live in
  `src/core/wwr/policy.cppm` — not wwr's unrelated
  `kit::AbortPolicy`. There is no recoverable mode and no
  `Result` to check after constructing a wrapper — recovery was cut as YAGNI;
  if a site ever needs it, add a reporting policy for that site, not a
  tree-wide switch. Use the aliases in `free_breakfast.core.wwr` (`Device`,
  `Buffers`, …, directly in `free_breakfast`) rather than naming a wwr policy.
  See `src/core/wwr/README.md`.
- **`BUILD_JOBS` (default 12, `devtools/config.sh`) is capped below what Ninja
  would pick, on purpose.** A module build is
  memory-hungry per job; an OOM-killed compiler surfaces as a bare
  `ninja: build stopped` with nothing about memory in it.
- **The auxiliary basis's angular-momentum limit is its own, and higher than
  the orbital one.** `kMaxAngularMomentum` (f) is the *orbital* ceiling;
  density fitting's aux shells run to i (`kMetricMaxMomentum`,
  `kThreeCenterAuxMaxMomentum`, `tools/emit/df_kernels.py`'s `AUX_MAX_L`
  against its `MAX_L`), because a JKFIT or RI set carries shells two l above
  the orbital set it fits. Only `kThreeCenterMaxMomentum` is static_asserted
  equal to the tree-wide one. The JKFIT cc sets stop at g;
  `def2-universal-JKFIT` and the `*-acCD-6-6` sets reach h and i by name,
  beside the hand-built `test/gtest/data/df_high_aux/`. A generated acCD set
  must be capped at `--max-l 6` wherever its orbital set has g.

## Agent-specific

`.claude/settings.json` wires `devtools/hooks/protect-main.py` as a PreToolUse
hook on `Write|Edit|NotebookEdit`: it **blocks edits to the primary checkout**,
so work belongs in a `.claude/worktrees/<name>` worktree (the `worktree` skill)
or a container-backed sibling worktree (`devtools/worktree.sh`). The nested
`.claude/worktrees/` subtree is itself allowed. Escape hatch, for deliberate
work on main: `CLAUDE_ALLOW_MAIN_EDITS=1`. The guard fails **open** on any
error — a guard bug must never brick editing.

`devtools/hooks/session-env.py` runs at SessionStart and reports whether you are
on the host or in the container.

### Waiting on a run: never `until ! pgrep -f …`

**Start a long build or tier with `run_in_background` and wait for its exit
notice. Don't poll for it with a `pgrep -f` loop**: such a loop never exits. The
Bash tool runs a command as `bash -c '<the whole script>'`, so that shell's own
command line contains the pattern, and `pgrep -f` matches the full command line
and skips only its own PID, not its parent's. A loop like
`until ! pgrep -f "cpp-tier.sh --preset default"; do sleep 5; done` therefore
always finds itself. One sat for hours as the status bar's "1 shell still
running", while a parallel session ran the same bug. If you really must wait on
something you did not start, wait on its PID (`while kill -0 "$pid"; do …`) or
use the bracket trick (`pgrep -f "[c]pp-tier.sh …"`). When hunting a stray shell
with `ps | grep`, don't filter out `pgrep`, which hides exactly this loop.

### Worktrees

There are two kinds, and which one you can make depends on which side you are
on:

- **`.claude/worktrees/<name>`** — a lightweight `git worktree` inside the main
  checkout, made and swept by the `worktree` skill. Works on both sides; the
  only kind available inside the container.
- **Sibling worktrees** (`<root>/<name>`, next to `main/`) — made by
  `devtools/worktree.sh add`, each with its own devcontainer and named volumes
  (the `devbox` skill). **Host-only**: it drives docker, which the container
  does not have. `worktree.sh rm` tears down the container and volumes that
  `git worktree remove` would leak.

The eight skills in `.claude/skills/` are the tooling ones — `audit`, `devbox`,
`doctor`, `milestone`, `milestone-run`, `pr`, `test`, `worktree` — and they
apply to this tree as written. `milestone-run` executes what `milestone`
creates: one subagent per ready issue, each in a `.claude/worktrees/` checkout,
PRs merged serially by the orchestrator.

Three more came across in the hoist and were **removed**: `constants`,
`error-handling` and `memory-buffer` documented the *ancestor* project's
versions of those modules, and described its module tree in detail — which has
no place in a public repo. `src/core/constants` and `src/core/error_handling`
do exist here, with different APIs; each has its own README. There is no
`src/core/memory_buffer`: buffers come from `wwr.extension.memory_buffer` in the
WarpWraps submodule. If you want skills for these, write them against the local
modules (and the `wwr.*` surface for buffers) rather than restoring the old
ones.
