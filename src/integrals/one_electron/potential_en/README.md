# Potential (electron-nuclear)

The Cartesian electron-nuclear potential (nuclear attraction) matrix V on the
GPU, over the `v_{la}{lb}` kernels FelizJueves generates. Point nuclei.

## Module

`free_breakfast.integrals.one_electron.potential_en`, also re-exported by
`free_breakfast.integrals.one_electron` and `free_breakfast.integrals`.

## Design

`nuclear_attraction` runs `check_one_electron_build` and `check_nuclei`
(`launch`), zeroes the `CartesianMatrixAO`, and launches one generated kernel
per class, one thread per record, with every nucleus serial inside it. The
kernels read the overlap's record fields plus `p`, the product centre, and the
molecule's nuclear charges and positions (`NucleiView`). Each thread adds its values at
`(m, n)` and `(n, m)` with fp64 atomics, so V is symmetric to rounding, not
bitwise. Queued on `res.stream()`, each class on its own stream, forked from it
and joined back into it (`launch_each`), with no host
synchronization.

**`add_nuclear_attraction`** is the same build without the zeroing: it adds V
into whatever the matrix holds. `core_hamiltonian` uses it to add V on top of
the T that `kinetic` wrote, forming H in place. It runs the same checks.

**Each kernel has its own Boys function.** Every `v_*.cu` carries the same
`static __device__ double fj_boys(int32_t, double)` (FelizJueves's wide one:
the Kummer series below T = 125, the asymptote above, because a point charge
has no exponent to damp `T = ζ|P − C|²`); `static` keeps the ten copies from
colliding at the device link.

**The kernels.** `kernels/v_{00,01,02,03,11,12,13,22,23,33}.cu` (every `la <= lb <= 3`),
generated by `tools/emit_one_electron_kernels.py` and committed as emitted,
each one explicit specialization of the kernel template `potential_en`,
compiled as a source of the device library; `potential_en_launch.cu` includes
only `kernels/potential_en.h` and launches through its `potential_en_kernels`
table.

**The family layout** is `overlap/`'s; the parent README's "One layout per
kernel family" has the table.

**Limits.** f per shell (`launch`'s `kOneElectronMaxL`), `n_ao² ≤ INT32_MAX`, and the
nuclei on the call's device; each is `InvalidConfig` before anything is
launched. The records' AO offsets are not checked against the matrix's order.
One thread per record, and the kernels spill registers from `la + lb = 3`
(FelizJueves's `docs/implementation/one_electron.md`); a warp per record is
FelizJueves's named follow-up.

## Public API

| Symbol | Role |
|---|---|
| `nuclear_attraction(res, classes, molecule, v)` | `Status`: the Cartesian V into `v` |
| `add_nuclear_attraction(res, classes, molecule, m)` | `Status`: V added into `m`, which is not zeroed first |

## Usage

```cpp
import free_breakfast.integrals.mmd;
import free_breakfast.molecule;
import free_breakfast.integrals.one_electron.potential_en;
import free_breakfast.recipes.matrix_ao;
namespace fb = free_breakfast;

const auto classes = fb::primitive_pair_classes(res, basis);  // once per basis
const fb::Molecule molecule(res, atoms);                       // nuclei: once per geometry
fb::CartesianMatrixAO v(res, basis);
fb::Status status = fb::nuclear_attraction(res, *classes, molecule, v);
```

## Tests

`test/gtest/core_hamiltonian_gpu.cpp`: H₂O in STO-3G and cc-pVDZ against
libcint's `int1e_nuc` at 1e-12 · max|V|, plus the zeroing and the class-range
refusal. `add_nuclear_attraction` is covered through `core_hamiltonian`'s
cases.
