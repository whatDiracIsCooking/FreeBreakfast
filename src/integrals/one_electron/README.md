# One-electron

One-electron integral matrices on the GPU, over kernels FelizJueves generates:
the overlap S, the kinetic energy T, the nuclear attraction V, and the core
Hamiltonian H = T + V.

> **Currently disabled:** `kinetic/`, `potential_en/` and `core_hamiltonian/`
> are not built, linked or re-exported, and `core_hamiltonian_gpu.cpp` is off;
> only `upload/` and `overlap/` are live. The sources are kept, and
> `CMakeLists.txt` says what to uncomment to restore them.

## Module

`free_breakfast.integrals.one_electron`, a convenience module that re-exports
the five below (and is itself re-exported by `free_breakfast.integrals`):

```
upload/            free_breakfast.integrals.one_electron.upload: the device records and nuclei, and the shared pre-launch checks
overlap/           free_breakfast.integrals.one_electron.overlap: the overlap S
kinetic/           free_breakfast.integrals.one_electron.kinetic: the kinetic energy T
potential_en/      free_breakfast.integrals.one_electron.potential_en: the electron-nuclear potential V
core_hamiltonian/  free_breakfast.integrals.one_electron.core_hamiltonian: H = T + V, in place
```

## Design

`upload_primitive_pairs` copies `mmd`'s records to the device once per basis,
and `upload_nuclei` a molecule's nuclei (Z and position) once per geometry (both
`upload`). A build then zeroes a `CartesianMatrixAO` and launches one generated
kernel per class, one thread per record: `s_{la}{lb}` for S, `t_{la}{lb}` for
T, `v_{la}{lb}` for V (the nuclei serial inside each record). Each thread adds
its values at `(m, n)` and `(n, m)` with fp64 atomics, so a matrix is symmetric
to rounding (the two mirror positions are summed in different orders), not
bitwise. The spherical matrix is `MatrixAOPair::cartesian_to_spherical` of the
result.

**One layout per kernel family.** `overlap/`, `kinetic/` and `potential_en/`
are each the same set of files, named after the directory:

| File | Role |
|---|---|
| `<family>.cppm` / `<family>.cpp` | The module and its build |
| `<family>_bridge.h` | The launcher's declaration, over `upload`'s device views, shared by the `.cu` and the implementation unit's global module fragment |
| `<family>_launch.cu` | The launcher, the family's own device library |
| `kernels/` | The generated kernels, and the `.clang-format` that leaves them unformatted |
| `CMakeLists.txt` | The device library `….<family>.device` and the module |

Every family takes its inputs, and its pre-launch checks
(`check_one_electron_build`, `check_nuclei`), from `upload`, and is bounded by
`basis`'s `kMaxAngularMomentum`, the one limit for the repo.
`core_hamiltonian/` has no kernels of its own, so it is only the module.

**H is built in place.** `core_hamiltonian` checks every input, then
`kinetic` zeroes H and writes T, and `add_nuclear_attraction` adds V on top.
Both only add, so T + V is formed without a T or V matrix of its own and
without a separate addition.

**The kernels.** Each family's `kernels/{00,01,02,11,12,22}.cu` (every
`la <= lb <= 2`), generated by `tools/emit_one_electron_kernels.py` and
committed as emitted. They are FelizJueves's vendor-neutral `gpu` spelling:
each includes FelizJueves's own `felizjueves/runtime.h` (`felizjueves::headers`,
linked PRIVATE by every family's device library), which selects the vendor
runtime from the compiler's own macros, so the same text compiles under nvcc
and clang `-x hip` with nothing of wwr in it. They have no warp shuffle, so no
wavefront is written into them either. Each launcher `#include`s its family's kernels rather than compiling them as
sources of their own, so it launches kernels whose definitions it can see;
listing them as sources too would define each `extern "C"` kernel twice.

**V's kernels each carry their own Boys function.** Every `v_*.cu` defines the
same non-static `__device__ double fj_boys(int, double)` (FelizJueves's wide
one: the Kummer series below T = 125, the asymptote above, because a point
charge has no exponent to damp `T = ζ|P − C|²`). Six of them in one TU would
define it six times, so `potential_en_launch.cu` includes each inside a
namespace of its own (`device::potential_en_{la}{lb}`), after including
`felizjueves/runtime.h` itself at file scope so that no namespace receives the
vendor runtime. The emitted text is untouched.

**Limits.**

- d per shell (`kMaxAngularMomentum`); a class above is `InvalidConfig`,
  before anything is launched.
- The kernels index the matrix as a 32-bit `m * n_ao + n`, so
  `n_ao² ≤ INT32_MAX` (about 46k Cartesian AOs); above is `InvalidConfig`.
- The records' AO offsets are not checked against the matrix's order: the
  classes must come from the basis the matrix was made for.
- V is one thread per record with every nucleus serial inside it, and its
  kernels spill registers from `la + lb = 3` (FelizJueves's
  `docs/implementation/one_electron.md`). A warp per record is FelizJueves's
  named follow-up.

## Public API

Everything the five sub-modules export; each README has its own table.

| Symbol | Module |
|---|---|
| `DevicePrimitivePairClass`, `DeviceNuclei`, their views, the uploads and checks | `upload` |
| `overlap(res, classes, s)` | `overlap` |
| `kinetic(res, classes, t)` | `kinetic` |
| `nuclear_attraction(res, classes, nuclei, v)`, `add_nuclear_attraction(…)` | `potential_en` |
| `core_hamiltonian(res, classes, nuclei, h)` | `core_hamiltonian` |

Every build is queued on `res.stream()`, with no host synchronization.

## Usage

```cpp
import free_breakfast.integrals;
import free_breakfast.linalg.matrix_ao;
namespace fb = free_breakfast;

const auto classes = fb::primitive_pair_classes(basis);       // host
const auto device = fb::upload_primitive_pairs(res, classes);  // once per basis
const auto nuclei = fb::upload_nuclei(res, molecule);          // once per geometry
fb::CartesianMatrixAO s(res, basis);
fb::CartesianMatrixAO h(res, basis);
fb::Status status = fb::overlap(res, *device, s);
status = fb::core_hamiltonian(res, *device, *nuclei, h);
```

## Tests

- `test/gtest/overlap_gpu.cpp`: H₂O in STO-3G and cc-pVDZ against libcint's
  `int1e_ovlp` at 1e-12 · max|S|, plus the zeroing and the class-range refusal.
- `test/gtest/core_hamiltonian_gpu.cpp`: the same two molecules' T, V and H
  against libcint's `int1e_kin` and `int1e_nuc` and PySCF's `hcore`, at the
  same tolerance, plus each build's zeroing and class-range refusal, and
  `upload_nuclei`'s refusal of an empty molecule.
