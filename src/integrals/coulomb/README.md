# Coulomb

The Cartesian Coulomb matrix `J_µν = Σ_λσ (µν|λσ) D_λσ` of an AO density, by
McMurchie–Davidson, on the GPU, from kernels generated by
[FelizJueves](../../../deps/FelizJueves). **Schwarz-screened** at `tau`
(default `1e-10`): each ket class is sorted descending by its bound `Iq · Dmax`
([`sort_bounds/`](sort_bounds/README.md)), and `e_hermite` stops a lane at its
first ket under `tau`. Its records are `mmd`'s, or, read in their place, a
copy with the negligible primitive pairs **pruned** (`coulomb_pair_classes`,
once per basis), **which assumes `|D_cd| <= 2`** (below).

## Module

`free_breakfast.integrals.coulomb`, also re-exported by
`free_breakfast.integrals`.

## Design

FelizJueves's `docs/implementation/j_engine.md`, "The J chain as device code",
is the contract the kernels were built against. Every class of
`free_breakfast.integrals.mmd`'s records is both a ket class and a bra class.
Each record's Schwarz bound `I = pair_bound(ζ, la + lb)`, `e_hermite`'s `Ip`
as a bra and `Iq` as a ket, is not formed here: it depends on ζ and `la + lb`
only, so it is `mmd`'s `bound` field, formed once per basis
([`../mmd/`](../mmd/README.md)), and a build reads it.

| Step | Template | One per | Computes |
|---|---|---|---|
| ket pre-contraction | `dq<lc, ld>` | ket pair class, `lc <= ld` | `D_q = w Σ_cd D_cd s E^cd_q` and `Dmax = max_q \|D_q\|`, reading the AO density in place |
| ket sort | `SortedKets::sort` (not generated) | ket pair class | the class's records sorted descending by `Iq · Dmax`, and `zeta`, P, `Iq`, `Dmax` and `D_q` gathered into that order |
| `[p\|q]` | `e_hermite<lp, lq>` | (bra class, ket class), `lp = la + lb`, `lq = lc + ld` | `J_p += Σ_q [p\|q] D_q`, one warp per bra record, kets strip-mined, `J_p` added atomically |
| bra transform + scatter | `jab<la, lb>` | bra pair class | `J_ab += Σ_p s E^ab_p J_p`, added atomically into `J_µν` at (m, n) and (n, m) |

`coulomb(res, classes, density, j)` runs them as two phases of
`launch_each` (the one-electron builds' per-class launch, reused with their
pre-launch checks from `free_breakfast.integrals.one_electron.launch`):

1. On `res.stream()`: zero `J` and every class's `J_p`, and fill `row` below.
2. **Every class's inputs**, each on its own stream: its records' weights `w`,
   then `dq`, then the ket sort (keyed on the class's `bound` times `Dmax`). The join closes
   the phase, because every bra class reads every ket class's sorted bounds,
   `D_q` and `Dmax`.
3. **Every class as a bra**, each on its own stream: `e_hermite` against every
   ket class, sorted, into the bra's `J_p`, then `jab` into `J`, in that order.
   The bra side reads its class in record order, which `mmd` makes
   descending ζ, so descending `Ip`: the bras with the longest ket loops
   launch first, once per basis and at no cost per build.

What the kernels leave to the launcher, and how it is supplied:

| Input | Value | Why |
|---|---|---|
| `w` | 2 for a shell pair of two shells, 1 for a shell against itself (`off_a == off_b`, as `mmd` records it) | `mmd` stores each unique shell pair once; the sum over all `(c, d)` counts the others twice. A one-thread kernel in `coulomb_launch.cu` writes it per build |
| `Ip`, `Iq` | the bra's `bound` field (`mmd`'s) in record order, the ket's sorted copy (`SortedKets::bound`) | The screen is `Dmax · Ip · Iq < tau` |
| `tau` | `coulomb`'s, default `1e-10` | The screen `break`s on a lane's first ket under `tau`, which is right only for kets sorted descending by `Iq · Dmax`: so they are |
| `row` | the record index | `jab` reads record `k`'s row of `J_p`; with one batch per class that row is `k` |
| `J`, `J_p` | zeroed | Both are only added to |
| the block | `e_hermite_block_dim`, `{1, FJ_WAVEFRONT}` | `e_hermite`'s shared `J_p` accumulator is sized for exactly that block |

The scratch, per class `n_rec × n_hermite(la + lb)` doubles for `D_q`, as many
for the sorted `D_q` and as many for `J_p`, plus `2 n_rec` for `w`
and `Dmax` and `10 n_rec` for the sort (its keys, its permutation, each with an
alternate, and the six sorted per-record arrays), is drawn from
`res.device()`'s pool in `res.stream()`'s order and returned in its order once
both phases are joined back, so there is no host synchronization.

**The swap needs nothing.** `mmd` stores a pair whose bra has the higher
momentum swapped; `dq` reads the symmetric density at the record's own offsets
(FelizJueves's `density="ao"`) and `jab` writes `J` and its mirror, so neither
orientation is ever transposed.

**One text serves both warp widths.** `e_hermite` is emitted `any_wavefront`:
its shuffles and its shared array read `FJ_WAVEFRONT`, which
`deps/CMakeLists.txt` sets from `WWR_WARP_SIZE`. `dq` and `jab`
have no shuffle. Record vectors are three flat arrays per axis, named as `mmd` names its
fields.

**`D_q` is q-major.** `dq` writes `D_q` as `D[n_hermite, n_rec]` and
`e_hermite` reads it so (FelizJueves's `passes.transpose` on both, applied by
the emitter): `e_hermite`'s lanes are consecutive kets, so a warp reads
`D[q * n_ket + k]` contiguously, where record-major put each lane `n_q`
doubles apart. EXESS's J engine transposes `D_q` for the same reason
(`[Fock]` §4.2). The ket gather keeps the layout, moving columns. `J_p`
stays record-major: each warp owns one bra's row.

**Generated kernels are committed, not built.** `tools/emit_coulomb_kernels.py`
writes `kernels/` from the FelizJueves submodule; re-run it after bumping the
submodule. `kernels/.clang-format` turns formatting off, and
`devtools/check-int-types.py` skips a file by FelizJueves's banner, so the files
stay byte-for-byte as emitted: a fix belongs in the generator.

## Pruning

`coulomb_pair_classes(res, classes, tau = 1e-13)` copies `mmd`'s classes
without the records J cannot need: arXiv:2407.21445 §3.2's primitive-pair
pruning, for two-electron records only. `mmd`'s own records are untouched,
because S, T and V read them and their correctness must not hang on a
two-electron bound.

**Why J needs it.** `mmd`'s `bound`, J's `Ip`, is `Σ_p I_p(ζ)`: it has no pair
factor `exp(-αβ/ζ |AB|²)` and no contraction coefficients, so it does not fall
with `|AB|`. The pair factor reaches J only through `s E^ab_p`, in `D_q` (a
ket) and in `jab` (a bra). So a far ket's `Dmax` is tiny and the sorted kets
stop early, but a far **bra** is never screened: its warp runs every ket a
near bra would, and `jab` then multiplies the result by `s E^ab_p ≈ 0`. On a
chain the far pairs are almost all of them.

**The bound, and the density it assumes.** Each record's dressed bound
`B = max_{i∈a} Σ_{k∈b} Σ_p |s E^{ik}_p| I_p(ζ)` is FelizJueves's
`ao.k.record_bounds` in `mmd`'s orientation, by the same generated
`record_bound<la, lb>` K reads (`mmd`'s `ordered_pair_bound`, over `mmd`'s
view). With `|[p|q]| <= I_p I_q`, the term of a bra record `(a, b)` and
a ket record `(c, d)` in any element of J is at most `B_ab · Dc · K_cd`, where
`K = w · ncart(la) · B` bounds the ket's sum over every Cartesian pair (`w`
as above) and **`Dc = 2` caps every `|D_cd|`**. A record goes when it is under
`tau` both ways, `B_r Dc max K < tau` and `K_r Dc max B < tau`. The cap is an
assumption, not a theorem, and `coulomb` does not check it: a closed-shell
density has `|D_cd| <= sqrt(D_cc D_dd)` and `D_cc <= 2 (S⁻¹)_cc`, which is 2
for a normalized AO that overlaps nothing and grows with the overlap, without
bound toward linear dependence. The H₁₀ chain's RHF density has `max|D|` 0.33;
the H₂O goldens' Hilbert densities, 1.

**The threshold is `1e-13`, not J's `1e-10`.** Each pruned term is under it,
but an element sums many: on the H₁₀ chain (the measurement's density, below)
pruning at `1e-10` moves J by 6.6e-12 · max|J|, past the libcint bar; at
`1e-11`, 3.5e-13; at `1e-12`, 6.7e-14; at `1e-13`, 7.9e-15. The pair factor
falls so fast that the record count barely moves with it: on H₂₀₀, 3.8% kept
at `1e-10`, 4.4% at `1e-13`, and J's time the same to 15%.

**Measured** on the RX 9060 XT (gfx1200, `--preset hip`, Release), median of
11 runs after one warm-up, J at its default `tau = 1e-10`. The chain is the
H₁₀ golden's H₂ unit (1.4 bohr bond, 5.4 bohr period, cc-pVDZ, 10 Cartesian
AOs) repeated; its density is the H₁₀ RHF density's blocks by unit
separation, the most central pair of H₁₀ at each separation up to 4 units,
past that the 4-unit block times `exp(-0.397 · 5.4 · (d − 4))` (the H₁₀ fit,
`../exchange/README.md`), zero under `1e-30`:

| Chain | AOs | Records kept | J, every record | J, pruned | Change | J moved |
|---|---|---|---|---|---|---|
| H₁₀ | 50 | 842 of 1,305 (65%) | 2.42 ms | 2.01 ms | −17% | 8e-15 |
| H₂₀ | 100 | 1,947 of 5,110 (38%) | 9.18 ms | 4.61 ms | −50% | 8e-15 |
| H₅₀ | 250 | 5,262 of 31,525 (17%) | 123 ms | 21.5 ms | −83% | 8e-15 |
| H₁₀₀ | 500 | 10,787 of 125,550 (8.6%) | 828 ms | 74.2 ms | −91% | 9e-15 |
| H₂₀₀ | 1,000 | 21,837 of 501,100 (4.4%) | 6,107 ms | 268 ms | −96% | 9e-15 |

"J moved" is `max|J_pruned − J| / max|J|`. The pruning itself is once per
basis: 8–17 ms over these. The records kept grow linearly with the chain, every
record quadratically, and so does the memory they hold. The timing program was
a throwaway, not kept in `bench/`.

## Not done

- **Reuse across SCF iterations.** The scratch is allocated per call.
- **Batching.** One `e_hermite` kernel per class, as FelizJueves ships it.
- **A checked cap.** `coulomb` does not check its density against
  `coulomb_pair_classes`' `|D_cd| <= 2`; the classes do not carry the
  threshold they were pruned at.
- **A dressed `Ip`.** Pruning drops the far bras once per basis; a bra screen
  on a dressed bound would drop them per density instead, which is a change to
  J's screen and its guarantee (#132 left J's screen out of scope).

## Public API

| Symbol | Role |
|---|---|
| `coulomb(res, classes, density, j, tau = 1e-10)` | `Status`: the Cartesian J of `density` into `j`, screened at `tau` (`0` screens nothing). InvalidConfig for a negative or NaN `tau`, another device, a density of another order, a class above d, or `j.n()^2` past `INT32_MAX` |
| `coulomb_pair_classes(res, classes, tau = 1e-13)` | `Result<std::vector<PrimitivePairClass>>`: a copy of `classes` (`primitive_pair_classes` of one basis) without every record whose J terms, as bra and as ket, are all under `tau` **for any density with `\|D_cd\| <= 2`** (above), each class in `mmd`'s record order on a new `DeviceStream`, an emptied class left out; for `coulomb` in place of `classes`. `tau = 0` keeps every record. InvalidConfig for a negative or NaN `tau` or a class above d |

## Tests

`test/gtest/coulomb_gpu.cpp`: `J` of H₂O in STO-3G and cc-pVDZ against
libcint's `vj` of the same density at `1e-12 · max|J|`, through the golden data
in `test/gtest/data/coulomb/`, both at `tau = 0` and at the default (each run
records its worst error, and how far the screen moved `J`); a `tau` above every
bound gives exactly zero, which shows the screen reaches the kernel and fires;
the zeroing; and the refusals. `tau` bounds each skipped term of a `J_p`, not
the error in `J`, so the screened bar is the same measured `1e-12`, not one
derived from `tau`. The bound the screen reads is `mmd`'s, and
`mmd_gpu.cpp`'s test. The sort itself is
[`sort_bounds/`](sort_bounds/README.md)'s test.

The pruned records (`coulomb_pair_classes` at its default): J from them against
the same goldens at `1e-12 · max|J|`, at `tau = 0` on H₂O in STO-3G and
cc-pVDZ and on the H₁₀ chain (`data/coulomb/h10_chain_ccpvdz.json`, its RHF
density), and at the default screen on the two H₂O (the chain's screened J
misses the bar with every record too); the record counts pinned, 135 of 135
kept in STO-3G, 572 of 593 in cc-pVDZ and 842 of 1,305 on the chain; how far
pruning moved J recorded (2.0e-14 on the chain, its worst error 2.0e-14);
every kept record, read back from the device, one of `mmd`'s with every field,
in `mmd`'s order; `tau = 0` keeping every record and a `tau` above every bound
none; and the refusals.
